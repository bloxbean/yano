# ADR-UTXO-005: Scalable EUTxO Lifecycle Indexer and Unified Console Experience

- Status: Accepted and implemented
- Version: v2
- Date: 2026-07-26
- Owners: App-chain / EUTxO / Console / Runtime
- Related: ADR-UTXO-001, ADR-UTXO-003, ADR-UTXO-004, ADR-022, ADR-028

## 1. Decision in plain words

Yano will provide an optional, node-local EUTxO lifecycle indexer. The
indexer will turn finalized EUTxO, Cardano bridge, and optional validity-proof
records into a query-oriented read model without changing app-chain consensus.

The first implementation will use SQLite through JDBC and Flyway-managed,
versioned SQL migrations. Storage will be hidden behind a small EUTxO
index-store contract so a future JDBC URL can select a tested PostgreSQL
dialect and a future separate module can provide RocksDB.

The modules will live with the other EUTxO extensions:

```text
appchain/extensions/eutxo/
  appchain-eutxo-indexer-core/
  appchain-eutxo-indexer-jdbc/

Future, only when justified:
  appchain-eutxo-indexer-rocksdb/
```

The index database is derived data. It does not participate in transaction
validation, state-root calculation, finality, anchoring, bridge authorization,
proof verification, or settlement. A missing or delayed index may make the
Explorer temporarily incomplete, but it must never stop consensus or change
user funds.

The existing `/ui/app-chain/eutxo/` route will use the indexer endpoints to
present a coherent, user-friendly flow:

```text
L1 deposit
  -> accepted vault output
  -> mirrored L2 EUTxO
  -> L2 transactions
  -> withdrawal claim
  -> optional validity batch and proof
  -> L1 root settlement
  -> L1 withdrawal payout
```

The UI will not use the disposable demo journal as a data source.

EUTxO clusters generated by `./yano.sh appchain eutxo demo up` will enable the
SQLite indexer automatically. This applies to both direct and ZK demo
scenarios, so a completed round-trip is immediately visible through the
unified console without additional database setup.

### 1.1 v2 implementation outcome

Milestones IX-M0 through IX-M7 are implemented. Review during IX-M7 replaced
the initial startup-time full in-memory projection with Flyway schema v2:
SQLite now owns both the durable event journal and bounded relational read
projection. Restart memory no longer grows with complete indexed history.
Atomic foreign-keyed rows make exact app-height rollback restore transaction,
deposit, account, and versioned withdrawal views together.

The release includes:

- storage-neutral index contracts and an in-memory conformance provider;
- Flyway-managed SQLite with startup integrity checks, recovery, rollback,
  shadow rebuild, and bounded prepared queries;
- asynchronous finalized-block catch-up and Micrometer metrics;
- a read-only `index/v1` domain API and derived-data envelopes;
- automatic direct and ZK demo integration across every generated node;
- the unified transaction/account/bridge/validity console;
- committed bridge-halt diagnostics without deletion of accepted history; and
- a reproducible benchmark and operator runbook.

The first release keeps destructive rebuild as a stopped-node, marker-checked
operator procedure. `demo status` and `demo verify` provide the quick-start
status and digest checks. Dedicated generic `yano.sh ... indexer` mutation
commands are deferred until they can coordinate safely with a live node.

## 2. Context

ADR-UTXO-004 added a safe EUTxO Explorer over deterministic transaction
summaries stored in committed app state. It decodes Cardano-shaped L2
transactions and supports lookup by L2 transaction ID or app-message ID.

That implementation intentionally stops at the state-machine boundary. It
does not provide one scalable query surface joining:

- the L1 staging and accepted-vault transactions;
- the exact stable L1 outpoint credited on L2;
- the mirrored L2 outpoint;
- all L2 transactions consuming and producing related value;
- the withdrawal-producing L2 transaction;
- the withdrawal claim;
- the optional ZK batch, proof, validity roots, and L1 root settlement; and
- the final L1 payout transaction and stable observation.

The disposable demo records many of these links in
`runtime/journal/operations.json`. That journal is useful for resumable demo
orchestration, but it is not canonical chain history, is not synchronized,
and does not cover transactions submitted outside the demo.

Querying several state paths and L1 endpoints for every page render would
create expensive fan-out, make pagination difficult, and couple the browser to
bridge and proof internals. Keeping an ever-growing query history in
consensus state would increase state size and make retention a consensus
decision.

Users nevertheless need a product view, not a demo-specific report:

```text
account -> deposits -> current EUTxOs -> L2 activity
        -> withdrawal claims -> L1 settlements
```

The product also needs to support direct EUTxO and ZeroJ-enabled EUTxO with
one read model and one console route.

## 3. Decision drivers

1. The index must not affect consensus latency or state roots.
2. Every displayed relationship must be traceable to canonical L1 or
   finalized L2 records.
3. The implementation must be rebuildable and rollback-safe.
4. The normal distribution must remain easy to run with no external database.
5. Address, transaction, claim, and lifecycle queries must be bounded and
   cursor-paginated.
6. The same base index must support direct and ZK EUTxO profiles.
7. Storage must be replaceable without changing projection or console logic.
8. The browser must not decode arbitrary Cardano, bridge, or proof CBOR.
9. Missing, partial, rebuilding, or stale index coverage must be visible.
10. No index database, index checkpoint, or demo journal may become a
    security or settlement authority.

## 4. Scope

### 4.1 Included

- Node-local projection of finalized EUTxO transactions.
- Current indexed UTxOs and address activity.
- Stable L1 deposit-to-L2 mirror correlation.
- L2 transaction lineage required to explain deposits and withdrawals.
- Withdrawal claim-to-L1 settlement correlation.
- Optional validity-batch, proof, and root-settlement metadata.
- SQLite/JDBC storage, schema migration, checkpointing, rollback, and rebuild.
- A bounded read-only domain API.
- EUTxO Explorer integration in the unified Svelte console.
- Health, lag, coverage, storage, and rebuild observability.
- Packaged JVM distribution and multi-node acceptance.

### 4.2 Not included

- Consensus validation or state-root calculation from SQLite.
- Synchronizing SQLite files or index rows over app-chain n2n.
- Using sinks as the authoritative built-in index.
- A general Cardano chain index, db-sync replacement, or block explorer.
- Arbitrary SQL, GraphQL, PromQL, or plugin-controlled browser queries.
- Full-text search over arbitrary datum or payload content.
- Storing private keys, mnemonics, witnesses, proof secrets, or API keys.
- PostgreSQL and RocksDB implementations in the first delivery.
- Production analytics, warehousing, or indefinite high-volume retention.
- Executable UI code supplied by a plugin.

## 5. Architecture

### 5.1 Data flow

```text
                      existing app-chain n2n
                              |
                              v
                    finalized app-chain blocks
                              |
                    committed EUTxO records
                              |
                              v
                  EUTxO projection engine
                              |
                      EutxoIndexStore
                              |
                   +----------+----------+
                   |                     |
             JDBC / SQLite        future RocksDB
                   |
                   v
             bounded domain API
                   |
                   v
       /ui/app-chain/eutxo/ unified console
```

The index itself is never sent over n2n. Every participating node already
receives finalized app blocks through app-chain n2n and can independently
derive the same logical projection. Node-local operational fields such as lag,
database size, and last local error may differ.

A sink is not required. Existing finalized-block sinks remain useful for
external PostgreSQL, Kafka, analytics, or custom applications, but an
external sink cannot be the source of truth for the bundled Explorer.

### 5.2 Canonical source boundary

The indexer projects facts from:

1. finalized app blocks available through `AppChainGateway`;
2. deterministic `EutxoTransactionSummary` and receipt queries;
3. committed `EutxoDepositRecord` values;
4. committed `EutxoWithdrawalClaim` values;
5. committed `EutxoWithdrawalConfirmation` values; and
6. committed neutral validity-batch and root-settlement records when the
   selected profile provides them.

The deposit contract already carries the accepted L1 outpoint, stable L1 slot
and block hash, staging outpoint, L2 address, and deterministic mirrored
outpoint. The withdrawal confirmation already carries the claim ID, L1
settlement transaction ID, payout index, stable L1 slot and block hash.

Milestone IX-M0 must audit the currently enumerable committed state and add
only the bounded deterministic indexes or neutral validity records needed for
complete replay. Any relationship that exists only in the demo journal is not
eligible for the product API until it has a canonical source.

### 5.3 Existing committed summary

ADR-UTXO-004's committed transaction summaries remain authoritative and
proofable. This ADR does not remove or reinterpret them.

The first indexer release is additive:

- committed state proves individual receipts and current consensus facts;
- the node-local index provides scalable history, relationships, filters, and
  account views; and
- the API identifies its output as a derived projection rather than an MPF
  proof.

Whether a later consensus profile can prune or reduce the committed monotonic
summary index is a separate versioned decision.

### 5.4 Runtime integration

The indexer uses the existing `AppChainGateway.subscribeFinalized` callback.
The callback only records that work is available and returns immediately.
Decoding, state queries, and database writes run on an indexer-owned executor.

If the bounded notification queue is full, the callback does not block
consensus and does not discard canonical truth. It marks catch-up required;
the worker resumes from its durable checkpoint by reading retained finalized
blocks and committed records.

The current `DomainApiContext` exposes only root-fixed committed-state
queries. A node-local index must not be smuggled through global state or a
static singleton. Implementation may therefore add a narrow reusable
host-owned local-read-model query facade to the domain API context:

```java
interface LocalReadModelQueryService {
    LocalReadModelResult query(
            String modelId,
            String chainId,
            String operation,
            byte[] boundedRequest);
}
```

It exposes no JDBC connection, filesystem path, mutable store, router, or
administration capability. The host continues to own routing, authentication,
request bounds, error redaction, and response limits.

## 6. Module boundaries

### 6.1 `appchain-eutxo-indexer-core`

This module contains:

- the storage and provider SPI;
- neutral source points and checkpoints;
- EUTxO projection events and models;
- transaction, address, bridge, and validity query models;
- projection orchestration and catch-up;
- rebuild and rollback coordination;
- the read-only domain API;
- health and metrics contracts; and
- a reusable EUTxO index-store conformance test suite.

It has no SQLite, PostgreSQL, RocksDB, ZeroJ, Quarkus, or console dependency.

### 6.2 `appchain-eutxo-indexer-jdbc`

This module contains:

- the normalized relational schema;
- JDBC transactions and prepared statements;
- Flyway Java-API integration and versioned SQL migrations;
- the SQLite JDBC driver;
- the SQLite dialect and safe default configuration;
- JDBC checkpoint and undo-journal storage; and
- JDBC store conformance and performance tests.

The module is designed to add a tested PostgreSQL dialect later. A URL alone
does not make an untested database supported. Version 1 accepts only
`jdbc:sqlite:` and fails closed for all other JDBC products.

Future PostgreSQL support requires:

- the PostgreSQL JDBC driver;
- PostgreSQL Flyway migrations and upsert behavior;
- the complete store conformance suite;
- shared-database writer coordination;
- failure/recovery and performance tests; and
- an explicit supported-version matrix.

The future URL form is:

```text
jdbc:postgresql://host:5432/database
```

Credentials are supplied separately, preferably through environment-backed
secret configuration, and are never embedded in generated project files.

### 6.3 Future `appchain-eutxo-indexer-rocksdb`

RocksDB cannot reuse JDBC or relational SQL directly. It will reuse:

- the core store contract;
- projection and query models;
- source-point and rollback semantics;
- rebuild behavior;
- health and metrics contracts; and
- the same conformance tests.

It will own its key encoding, secondary indexes, write batches, delta storage,
and schema migration.

### 6.4 Store contracts

The public contracts are domain-oriented:

```java
public interface EutxoIndexStore extends AutoCloseable {
    EutxoIndexWrite begin(SourceBlock sourceBlock);

    IndexCheckpoint checkpoint();

    void rollbackTo(SourcePoint sourcePoint);

    EutxoIndexReader reader();
}

public interface EutxoIndexWrite extends AutoCloseable {
    void apply(EutxoIndexEvent event);

    void commit(IndexCheckpoint checkpoint);

    void abort();
}

public interface EutxoIndexStoreProvider {
    String type();

    EutxoIndexStore open(EutxoIndexStoreContext context);
}
```

Applying all projection events for one source block and advancing the
checkpoint is one atomic store transaction. Storage-specific types never
escape these interfaces.

## 7. Node-local configuration and capability

The indexer is a node-scoped capability:

```text
indexer:eutxo-lifecycle
scope: node
selectable: false
availability: BUNDLED
maturity: preview
```

It is derived from the distribution and enabled automatically when:

- the indexer modules are present;
- at least one configured chain uses `eutxo-ledger`; and
- the operator has not disabled it.

Illustrative configuration:

```yaml
yano:
  app-chain:
    eutxo-indexer:
      enabled: true
      store:
        type: jdbc
        jdbc:
          # Empty means one derived local SQLite file per EUTxO chain.
          url: ""
```

An explicit single-chain SQLite URL may be configured:

```yaml
yano:
  app-chain:
    eutxo-indexer:
      store:
        type: jdbc
        jdbc:
          url: jdbc:sqlite:./data/indexes/payments-eutxo.db
```

When several EUTxO chains share a node, the default is one SQLite database per
chain. An explicit URL must contain a validated chain placeholder or startup
fails rather than mixing chain data.

### 7.1 EUTxO demo defaults

The disposable EUTxO demo generator enables the bundled JDBC/SQLite indexer in
every generated demo node. Each node owns a separate database:

```text
<workspace>/
  project/data/
    node0/appchains/<chain-id>/indexes/eutxo-lifecycle.db
    node1/appchains/<chain-id>/indexes/eutxo-lifecycle.db
    node2/appchains/<chain-id>/indexes/eutxo-lifecycle.db
```

Demo nodes never share one SQLite file. Enabling the index on every node makes
each node's console useful and exercises independent projection from the same
n2n-replicated finalized blocks. Production operators may enable it only on
dedicated API/explorer nodes.

For the `ledger`, `bridge`, and `zk` demo scenarios, including the
`eutxo-zeroj-preview` recipe:

1. `demo up` writes explicit node-local indexer configuration;
2. startup verifies that the SQLite driver is packaged and the derived index
   directory is writable;
3. readiness distinguishes node readiness from index readiness;
4. `demo status` reports every node's indexed height, finalized height, lag,
   coverage, and store type;
5. `demo round-trip` waits for the resulting lifecycle to become queryable
   before reporting success;
6. successful output prints the exact unified-console deep link; and
7. demo cleanup removes only marker-owned workspace index files.

Example successful output:

```text
ROUND_TRIP_COMPLETE
chain: payments-eutxo
index: READY_FULL (height 42, lag 0)
console: http://127.0.0.1:7070/ui/app-chain/eutxo/?chain=payments-eutxo
```

The demo journal remains responsible only for orchestration, idempotency, and
recovery of demo commands. The indexer reconstructs its data from canonical
records and never imports `runtime/journal/operations.json`.

Indexer configuration is node-local. It is excluded from:

- the consensus profile;
- app-chain locks and shared configuration digests;
- finality and anchor commitments; and
- project portability checks that compare consensus identity.

The database identity binds at least:

```text
schema version
network/protocol magic
chain ID
state-machine ID
EUTxO profile ID
bridge ABI, when present
validity profile, when present
```

An identity mismatch fails startup for that index. It never silently reuses,
truncates, or overwrites another chain's database.

## 8. Relational projection model

The initial logical schema contains:

```text
Flyway schema history
index_metadata
index_checkpoints
indexed_source_blocks
index_undo

l2_transactions
l2_transaction_inputs
l2_transaction_outputs
l2_utxos
address_activity

bridge_deposits
withdrawal_claims
l1_settlements
lifecycle_edges

validity_batches
validity_batch_transactions
validity_proofs
l1_root_settlements
```

The exact Flyway migration DDL is implementation-owned, but the logical
semantics are part of this decision.

### 8.1 Transaction identity

The index keeps these identities distinct:

| Identity | Meaning |
|---|---|
| app-message ID | One app-chain submission attempt |
| L2 transaction ID | Hash of the canonical Cardano-shaped L2 transaction body |
| L2 outpoint | L2 transaction ID plus output index |
| L1 transaction ID | Cardano L1 transaction hash |
| L1 outpoint | L1 transaction ID plus output index |
| claim ID | Deterministic withdrawal-claim identity |
| validity batch ID | One bounded validity batch |
| proof digest | Content identity of one proof |

A claim ID is not a message ID. The normal relation is:

```text
app-message ID
  -> L2 transaction ID
  -> withdrawal outpoint
  -> claim ID
  -> L1 settlement transaction ID
```

### 8.2 Lifecycle is a graph

Value provenance is not always one linear record. A transaction may merge
several deposits or split one deposit across many outputs. The index therefore
stores typed edges:

```text
L1_OUTPOINT_ACCEPTED -> L2_OUTPOINT_MIRRORED
L2_OUTPOINT_CONSUMED -> L2_TRANSACTION
L2_TRANSACTION       -> L2_OUTPOINT_CREATED
L2_OUTPOINT           -> WITHDRAWAL_CLAIM
WITHDRAWAL_CLAIM      -> L1_SETTLEMENT
L2_TRANSACTION        -> VALIDITY_BATCH
VALIDITY_BATCH        -> L1_ROOT_SETTLEMENT
```

The API may render a simple timeline when the graph is linear. When several
origins or descendants exist, the UI shows them explicitly rather than
inventing a one-to-one lifecycle.

Graph traversal is bounded by maximum depth, maximum nodes, and stable cursor.
Version 1 does not expose an arbitrary graph query language.

### 8.3 ZK reuse

Direct and ZeroJ-enabled EUTxO use the same base index. The ZeroJ modules
translate provider-specific runtime data into neutral validity records:

```text
provider
proof system
circuit profile
batch ID
ordered L2 transaction IDs
previous validity root
new validity root
batch-data commitment
proof digest
verification-key digest
proof status
L1 root-settlement transaction ID
L1 slot and block hash
```

`appchain-eutxo-indexer-core` does not depend on ZeroJ. A different future
validity provider can emit the same neutral records.

Large proving keys, private witnesses, and full proof artifacts are not copied
into every row. The index stores bounded metadata, content digests, and an
optional validated content-addressed artifact reference.

When validity settlement is absent, validity tables remain empty and the
console hides all validity sections.

## 9. Synchronization, checkpointing, and rebuild

### 9.1 Live indexing

For each finalized app block:

1. verify the expected next app height and previous hash;
2. obtain deterministic transaction and bridge results;
3. produce bounded `EutxoIndexEvent` values;
4. open one store write transaction;
5. write transactions, inputs, outputs, UTxOs, lifecycle edges, and optional
   validity records;
6. record the exact source block;
7. advance the checkpoint; and
8. commit once.

Duplicate replay of the same height and hash is idempotent. The same height
with a different hash is an identity error requiring rollback or rebuild.

### 9.2 Startup catch-up

On startup, the indexer:

1. validates database identity and schema;
2. reads its last checkpoint;
3. compares it with the app-chain ledger;
4. catches up retained finalized blocks in height order;
5. verifies the resulting logical tip; and
6. switches to live subscription.

The console remains available during catch-up and displays coverage and lag.
Queries never imply that unindexed heights are absent from the chain.

### 9.3 Full rebuild

A missing, corrupt, incompatible, or operator-discarded database is rebuilt
into a new temporary database:

```text
create schema
  -> replay canonical records
  -> verify checkpoint and counts
  -> atomically activate rebuilt database
```

The old database is not overwritten until the replacement passes validation.

Full historical rebuild requires at least one complete replay source:

1. retained finalized app blocks with bodies;
2. enumerable committed transaction, deposit, claim, confirmation, and
   validity indexes; or
3. a versioned verified projection snapshot plus all subsequent canonical
   records.

If the node has pruned data required for older history and has no qualifying
snapshot, the index reports `PARTIAL` coverage with the exact earliest
available height. It must not report a successful full rebuild.

The implementation must define and test the retention contract before
enabling automatic pruning of data needed by the indexer.

### 9.4 Coverage states

```text
DISABLED
STARTING
CATCHING_UP
READY_FULL
READY_PARTIAL
REBUILDING
DEGRADED
IDENTITY_MISMATCH
FAILED
```

`DEGRADED` means reads may continue through the last verified checkpoint.
`FAILED` means the index is not served. Neither state changes consensus.

## 10. Rollback and reorganization safety

### 10.1 Source points

Slot or height alone is insufficient because competing forks can contain
different blocks at the same slot or height.

An L1 source point contains:

```text
slot
block hash
previous block hash
block number, when available
```

An L2 source point contains:

```text
app height
app block hash
previous app block hash
message ordinal, for row provenance
```

### 10.2 No delete-by-slot shortcut

This is not sufficient:

```sql
DELETE FROM ... WHERE l1_slot > ?;
```

A row created before the rollback may have been changed after it. Deleting
new rows would not restore a previously spent UTxO, an earlier claim status,
or a prior aggregate.

Every store implementation must preserve the prior value for each mutation:

```text
create row -> undo deletes it
update row -> undo restores its exact prior value
delete row -> undo restores the deleted value
```

Undo entries are grouped and ordered by exact source block. Rollback walks
orphaned blocks backwards and applies their undo entries in reverse order in
one transaction per block or one bounded atomic rollback transaction.

### 10.3 Stable L1 facts versus pending observations

The canonical lifecycle index is driven by stable L1 facts accepted into
finalized app-chain state. App-chain finality does not roll back.

An optional future pending-L1 view may show pre-stability observations. Those
rows are explicitly `PENDING_LOCAL`, carry their exact L1 chain point, and are
removed or restored through the L1 undo journal during a normal rollback.
They are never included in reserve, credited-deposit, or settled-withdrawal
totals.

A rollback deeper than the configured L1 stability depth is not handled by
deleting finalized lifecycle history. ADR-UTXO-001 treats it as a catastrophic
bridge event. The indexer preserves the prior accepted record and appends or
projects the bridge halt/reconciliation state so the console shows the
discrepancy.

### 10.4 Conservative fallback

The index is discarded and rebuilt when:

- the rollback point predates retained undo history;
- an expected parent hash does not match;
- checkpoint and source-block records disagree;
- a migration invalidates old undo entries; or
- integrity checks cannot prove a safe local rollback.

## 11. Read-only API

### 11.1 API identity

The indexer contributes a manifested, read-only domain API:

```text
com.bloxbean.cardano.yano.appchain.eutxo.indexer
```

Base path:

```text
/api/v1/plugins/com.bloxbean.cardano.yano.appchain.eutxo.indexer/index/v1
```

The version belongs to the API contract, not the SQLite schema.

### 11.2 Common response envelope

Every successful response includes:

```json
{
  "apiVersion": "eutxo-index/v1",
  "chainId": "payments-eutxo",
  "stateMachineId": "eutxo-ledger",
  "projection": {
    "kind": "DERIVED",
    "status": "READY_FULL",
    "indexedHeight": 1042,
    "finalizedHeight": 1042,
    "lagBlocks": 0,
    "historyFromHeight": 1,
    "fullHistory": true
  },
  "data": {}
}
```

Derived responses are not described as state proofs. When a proof is
available, the response links the exact committed key, height, state root,
and proof endpoint separately.

### 11.3 Endpoint set

Let `B` be the base path above.

| Method and path | Purpose |
|---|---|
| `GET B/status?chain=` | Store type, schema, coverage, checkpoint, finalized height, lag, rebuild state, and bounded diagnostic code |
| `GET B/transactions?chain=&limit=&cursor=&address=&status=` | Newest-first bounded L2 transaction page |
| `GET B/transactions/{transactionId}?chain=` | One decoded L2 transaction with inputs, outputs, claims, batch, and bridge links |
| `GET B/messages/{messageId}?chain=` | Resolve an app-message attempt to its L2 transaction or rejection |
| `GET B/accounts/{address}?chain=` | Current indexed balance/UTxOs and bounded activity summary |
| `GET B/accounts/{address}/utxos?chain=&limit=&cursor=` | Current indexed UTxOs |
| `GET B/accounts/{address}/activity?chain=&limit=&cursor=&type=` | Deposits, L2 transactions, claims, and payouts affecting the address |
| `GET B/bridge/deposits?chain=&address=&limit=&cursor=&status=` | Stable deposit page |
| `GET B/bridge/deposits/{l1TxId}/{outputIndex}?chain=` | Accepted L1 deposit, mirror, and bounded descendant lineage |
| `GET B/bridge/withdrawals?chain=&address=&limit=&cursor=&status=` | Withdrawal-claim page |
| `GET B/bridge/withdrawals/{claimId}?chain=` | Claim, funding origins, L2 request, proof/batch, and L1 payout |
| `GET B/lineage/outpoints/{txId}/{outputIndex}?chain=&direction=&depth=` | Bounded provenance/descendant graph |
| `GET B/validity/batches?chain=&limit=&cursor=&status=` | Optional validity-batch page |
| `GET B/validity/batches/{batchId}?chain=` | Ordered transactions, roots, proof identity, DA commitment, and L1 root settlement |

Unknown optional validity capability returns a stable `CAPABILITY_UNAVAILABLE`
response. It is not represented as an empty proof history.

### 11.4 Pagination and query bounds

- Default page size: 25.
- Maximum page size: 100.
- Cursors are opaque, versioned, bounded, and tied to chain/query ordering.
- Offset pagination is not exposed.
- Address and identifier filters are exact and canonically validated.
- Lineage depth defaults to 2 and is at most 6.
- One lineage response contains at most 256 nodes and 512 edges.
- Responses are bounded by the host domain-API response ceiling.
- Unknown query parameters fail closed.
- No endpoint accepts SQL, arbitrary column names, arbitrary sort
  expressions, or regular expressions.

### 11.5 Lifecycle response

A withdrawal detail response contains enough information to render the full
flow without browser joins:

```json
{
  "claim": {
    "claimId": "…",
    "status": "L1_STABLE",
    "destinationAddress": "addr_test…",
    "lovelace": "5000000"
  },
  "l2Request": {
    "messageId": "…",
    "transactionId": "…",
    "outpoint": "…#0",
    "appHeight": 91,
    "appBlockHash": "…",
    "stateRoot": "…"
  },
  "fundingOrigins": [
    {
      "acceptedL1Outpoint": "…#0",
      "mirroredL2Outpoint": "…#0",
      "l1Slot": 8123,
      "l1BlockHash": "…"
    }
  ],
  "validity": null,
  "settlement": {
    "transactionId": "…",
    "payoutIndex": 0,
```

For a ZK chain, `validity` includes the batch, old/new roots, proof and
verification-key digests, verification status, data-availability commitment,
and L1 root-settlement transaction.

### 11.6 Error semantics

Stable bounded codes include:

```text
INDEX_DISABLED
INDEX_STARTING
INDEX_REBUILDING
INDEX_FAILED
INDEX_IDENTITY_MISMATCH
INDEX_PARTIAL_HISTORY
INVALID_CURSOR
INVALID_IDENTIFIER
CAPABILITY_UNAVAILABLE
NOT_FOUND
QUERY_LIMIT_EXCEEDED
```

Internal paths, JDBC URLs, SQL text, stack traces, credentials, and arbitrary
exception messages are never returned.

The first release exposes no remote rebuild, migration, or delete endpoint.
Those remain local operator commands.

### 11.7 L1 transaction-detail enrichment

The lifecycle index stores the bounded L1 facts required to remain useful:

```text
transaction ID and outpoint
slot and block hash
address and lovelace
bridge role and status
related deposit, claim, batch, or settlement identity
```

When a user opens an L1 stage, the console may lazily enrich it from the
connected Yano node's existing L1 APIs:

```text
GET /api/v1/txs/{txHash}
GET /api/v1/txs/{txHash}/utxos
```

The first endpoint supplies available transaction/block metadata such as
block hash and number, slot/time, transaction index, fee, validity interval,
and input/output count. The second supplies available resolved input/output
addresses, values, datum identity or inline datum, and reference-script
identity.

This enrichment applies to:

- the refundable staging transaction, when retained;
- the accepted-vault deposit transaction;
- the direct L1 withdrawal payout;
- the ZK validity-root settlement transaction; and
- the proof/nullifier withdrawal transaction.

The browser performs these calls only when detail is requested. The indexer
does not call its own node over loopback HTTP and does not duplicate complete
L1 transaction bodies in SQLite.

Before combining results, the UI compares the returned L1 block hash and slot
with the lifecycle record. A mismatch is shown as a provenance warning and
the two sources are not silently merged.

L1 detail is optional enrichment, not a lifecycle dependency. The API can
return `404` when the relevant block/history is not retained and `503` when
the node's UTxO state is disabled. In either case, the console continues to
show the canonical bounded lifecycle facts from the index and explains why
expanded L1 detail is unavailable.

The same resolved console API base, network identity, CORS policy, and
authentication handling used by ADR-028 apply to these calls. Version 1 does
not contact an external Cardano explorer automatically.

## 13. SQLite/JDBC operating profile

### 13.1 Flyway migration contract

`appchain-eutxo-indexer-jdbc` uses the Flyway Java API during store startup.
Flyway and any database-support module required by the selected release are
pinned in the Gradle dependency catalog and recorded in the release dependency
inventory and SBOM.

Migration resources are dialect-specific:

```text
appchain-eutxo-indexer-jdbc/
  src/main/resources/
    db/migration/eutxo/sqlite/
      V1__initial_eutxo_index.sql
      V2__example_forward_change.sql

Future:
    db/migration/eutxo/postgresql/
      V1__initial_eutxo_index.sql
      V2__example_forward_change.sql
```

Startup order is:

```text
resolve and validate JDBC dialect
  -> acquire exclusive local index startup ownership
  -> configure Flyway for the exact dialect location
  -> validate migration names and checksums
  -> migrate
  -> validate index identity
  -> verify checkpoint integrity
  -> start catch-up worker
  -> expose read endpoints
```

The migration rules are:

- migrations are forward-only, immutable after release, and checked into
  source control;
- every migration has deterministic tests from an empty database and every
  previously released schema version;
- SQLite and PostgreSQL use separate resource locations even when a migration
  happens to contain identical SQL;
- SQL migration files contain no explicit `BEGIN`, `COMMIT`, or Flyway
  `clean` operation;
- externally supplied placeholders, callbacks, locations, and migration
  scripts are not accepted;
- out-of-order migrations are disabled;
- baseline-on-migrate is disabled for an unexpected non-empty database;
- Flyway `clean` is disabled in the embedded runtime;
- checksum mismatch, unknown future schema, partial migration, or unsupported
  dialect prevents that index from serving reads;
- Flyway `repair` is never run automatically; and
- destructive or expensive data reshaping should rebuild the disposable
  projection from canonical records instead of carrying an unsafe in-place
  migration.

SQLite does not support concurrent Flyway migration locking in the same way
as a server database. This is compatible with the design because one Yano
process exclusively owns each local SQLite index file and migration completes
before the writer or read API starts.

The Flyway schema-history table and Yano's `index_metadata` serve different
purposes:

- Flyway history proves which database-schema migrations ran; and
- `index_metadata` binds the projection to network, chain, state-machine,
  profile, bridge ABI, validity profile, and replay coverage.

Neither substitutes for the other.

### 13.2 Defaults

The SQLite implementation uses a local filesystem and an indexer-owned writer:

```text
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
```

`NORMAL` is acceptable because the database is derived and restart catch-up
repairs loss of the latest committed index transaction. It must still
preserve database consistency. Operators may select a stricter supported
synchronous mode.

The implementation uses:

- one writer pipeline per database;
- prepared statements;
- one SQL transaction per app block;
- bounded read connections;
- keyset indexes matching every public query;
- bounded WAL checkpointing; and
- no SQLite database on a network filesystem.

### 13.3 Storage location

Default:

```text
<node-data>/
  appchains/
    <chain-id>/
      indexes/
        eutxo-lifecycle.db
```

Temporary rebuild files and WAL files remain inside that explicit index
directory. Cleanup commands validate an index marker and chain identity before
removing any derived file.

### 13.4 Scale posture

SQLite can technically hold multi-terabyte databases, but theoretical file
limits do not define Yano's production support level. Before release, the
implementation measures:

- bytes per representative payment, deposit, withdrawal, and validity batch;
- sustained live indexing throughput;
- catch-up throughput;
- p50/p95/p99 query latency at increasing data sizes;
- rollback and rebuild duration;
- WAL growth and checkpoint latency; and
- consensus overhead with the index enabled and disabled.

Provisional engineering objectives on a documented modern NVMe/JVM baseline:

```text
sustained indexing       >= 2,000 representative L2 payments/second
catch-up indexing        >= 5,000 representative L2 payments/second
common query p95         <= 200 ms at the tested supported dataset
finalized callback p99   <= 1 ms
consensus throughput     no material regression from indexer work
```

These are benchmark gates, not unmeasured product claims. The committed
schema-v2 baseline on Java 25/macOS arm64 indexed 20,000 representative
payments at 8,194 events/second, rebuilt at 11,562 events/second, used 2,995
database bytes/payment, kept common query p95 below 7 ms, and measured a
0.625-microsecond finalized-callback p99 while the writer was deliberately
stalled. The exact machine-readable report and reproduction command live in
`appchain/extensions/eutxo/benchmarks/` and `INDEXER_OPERATIONS.md`. These
figures are an engineering baseline, not a universal production capacity
claim.

For multi-terabyte retention, high availability, or sustained throughput
beyond the measured SQLite envelope, operators use an eventual tested
PostgreSQL provider or an external index built from finalized sinks. The
bundled console may use any conformant provider through the same API.

### 13.5 Backpressure

The indexer favors correctness over apparent freshness:

- it never drops a canonical block;
- it never blocks app-chain finalization waiting for SQLite;
- it records catch-up required when notifications overflow;
- it serves only through the last atomic checkpoint; and
- it reports lag and degraded status.

stopped-writer, and path-safety checks.

## 15. Security and correctness invariants

1. Index contents never authorize an L2 transition or L1 settlement.
2. SQLite failure never changes consensus state or app-chain finality.
3. The indexer never stores private keys, mnemonics, passwords, witness
   secrets, or proving secrets.
4. Every lifecycle edge identifies its canonical source record and source
   block.
5. Stable L1 status always includes both slot and block hash.
6. L2 provenance always includes app height and block hash.
7. Node-local pending L1 observations are visibly distinct from committed
   stable bridge facts.
8. A deep L1 rollback preserves the accepted history and surfaces bridge halt
   or reconciliation; it does not silently erase credited value.
9. Applying a block and advancing its checkpoint are atomic.
10. Aggregates are derived from rollback-safe row mutations, never updated
    without the corresponding prior-value delta.
11. Unknown schema, dialect, identity, cursor, or capability fails closed.
12. Pagination ordering is deterministic and stable.
13. The domain API exposes no SQL or storage-specific identifiers.
14. The console labels index data as derived and proof data with its exact
    root provenance.
15. Demo journal data is never merged into the product index.

## 16. Alternatives considered

### 16.1 Keep using the demo journal

Rejected. It covers only demo-owned operations, is not replicated, is not
canonical, and can be deleted independently of the chain.

### 16.2 Browser-side indexing

Rejected. It requires downloading history, duplicates parsing in untrusted
JavaScript, loses data across clients, and cannot provide a reliable
multi-user product view.

### 16.3 Query committed state and L1 APIs on every page

Rejected as the full solution. It remains useful for proofs and exact detail,
but repeated fan-out does not provide scalable account history, filters,
lineage, or pagination.

### 16.4 Put the complete explorer index in consensus state

Rejected. It increases every member's consensus state, makes retention a
consensus rule, and couples UI query patterns to state-root evolution.

### 16.5 Synchronize the index over n2n

Rejected. Finalized app blocks and committed records are already synchronized.
Replicating derived rows adds another protocol and another source of
divergence.

### 16.6 Build the index from a sink

Rejected for the built-in console. Sink delivery is at-least-once and
operator-configured. It is appropriate for external analytics, not required
for the default local product experience.

### 16.7 PostgreSQL-only

Rejected for the default because it destroys the zero-configuration
distribution experience. PostgreSQL remains a future JDBC provider for shared
and larger deployments.

### 16.8 RocksDB as the first implementation

Deferred. RocksDB matches write-heavy key/value workloads and already exists
elsewhere in Yano, but the EUTxO lifecycle view needs relational joins,
operator inspection, schema migration, and account/claim queries. SQLite is
the simpler first read-model store. The SPI preserves a RocksDB path.

### 16.9 One fully generic indexer framework before EUTxO

Deferred. EUTxO provides the first concrete lifecycle and rollback
requirements. Core contracts avoid unnecessary storage coupling, but a
general cross-state-machine index framework will be extracted only after a
second stock state machine proves the shared shape.

### 16.10 Hand-written schema versioning

Rejected. Custom migration bookkeeping would duplicate checksum, ordering,
history, validation, and failure semantics already provided by Flyway.
Yano-specific chain identity, checkpoints, and rebuild coverage remain in
`index_metadata`; relational schema evolution belongs to Flyway.

## 18. Build and release gates

- `appchain-eutxo-indexer-core` has no JDBC, SQLite, RocksDB, ZeroJ, Quarkus,
  or frontend dependency.
- `appchain-eutxo-indexer-jdbc` passes the complete store conformance suite.
- Flyway migrations validate from an empty database and every supported prior
  schema; released migration checksums are immutable.
- Flyway clean, automatic repair, out-of-order migration, and unexpected
  baseline are disabled.
- Unknown JDBC dialects fail before indexing starts.
- Store identity prevents cross-network and cross-chain database reuse.
- Index disable/failure does not change app state roots, blocks, finality, or
  anchoring.
- Multi-message, chained-transaction, split/merge, deposit, claim,
  confirmation, and validity fixtures replay identically.
- Rollback tests verify previous-value restoration for all mutable and
  aggregate rows.
- Deep L1 rollback is displayed as bridge risk, not silently erased history.
- API fuzzing covers malformed IDs, cursors, addresses, filters, oversized
  pages, traversal bounds, and response bounds.
- L1 enrichment tests cover matching and mismatched block provenance,
  disabled UTxO state, pruned/missing blocks, multi-asset outputs, bounded
  datum presentation, and standalone-console API-base handling.
- No secrets or unbounded witness/proof bytes appear in database fixtures,
  logs, metrics, APIs, or UI.
- Frontend tests cover loading, empty, partial, catching-up, degraded,
  identity-mismatch, direct, bridge, and ZK views.
- Browser tests cover wide, narrow, keyboard-only, copy feedback, and
  accessible lifecycle status.
- Packaged JVM tests serve the index API and console assets from the release
  distribution.
- Direct and ZK `./yano.sh appchain eutxo demo` acceptance tests verify
  automatic index enablement, per-node database isolation, index catch-up,
  status output, lifecycle visibility, restart, and safe cleanup.
- Current EUTxO native posture remains unchanged until the SQLite driver and
  complete EUTxO stack pass native acceptance.

## 19. Consequences

### 19.1 Positive

- Users can understand the complete bridge lifecycle in one built-in console.
- The same product surface supports direct and ZK EUTxO.
- SQLite preserves the default single-binary, no-external-database
  experience.
- Query load and history do not inflate consensus state or block finality.
- Operators can rebuild or replace a damaged index without risking funds.
- A future PostgreSQL or RocksDB backend does not change projection or UI
  contracts.
- The design establishes a concrete pattern that may later be extracted for
  other stock state-machine indexes.

### 19.2 Negative

- The distribution gains a native SQLite dependency and schema migration
  responsibility, plus the Flyway runtime dependency.
- Every index-enabled query node consumes additional CPU, memory, and disk.
- Historical rebuild depends on a clearly maintained canonical retention or
  snapshot contract.
- The application gains eventual consistency between finalized height and
  indexed height.
- Relational lineage and rollback add implementation and test complexity.
- A multi-terabyte local database remains operationally difficult even if
  SQLite permits it.

### 19.3 Neutral but important

- The index is not a proof. Proofable committed state and L1 verification
  remain separate.
- Nodes need not all enable the index. API/explorer nodes are the expected
  production placement.
- Two independently built indexes may differ in local lag while agreeing on
  all rows through the same checkpoint.
- PostgreSQL support is not delivered merely because JDBC is used.
- RocksDB remains a separate physical adapter, not a JDBC dialect.

## 20. Follow-on decisions

The following remain separate future decisions:

1. PostgreSQL shared-writer election, lease, or fully idempotent multi-writer
   operation.
2. RocksDB implementation after measured SQLite limits justify it.
3. Long-horizon verified index snapshots and archive distribution.
4. Retention/pruning of ADR-UTXO-004 committed historical summaries.
5. A generic `appchain-indexer-core` extracted after a second state machine
   demonstrates common requirements.
6. Operator-configured external Cardano explorer links.
7. Production support tiers for hundreds-of-gigabytes and multi-terabyte
   SQLite deployments.
