# ADR-025.1 Phase D: Validation Developer Experience

## Status

Implemented and qualified on 2026-08-04.

## Scope completed

Phase D makes genesis-bound value validation usable without weakening the
authoritative apply boundary.

1. The state CLI can validate a candidate offline from canonical genesis,
   inspect collections and validator digests, and explain error codes 0-12.
   Plugin validation without an exact application adapter reports
   `UNAVAILABLE`; it is never treated as acceptance.
2. `AuthenticatedMapPreflight` provides the same encoding and schema checks in
   the lightweight Java client. `StdlibAppChainClient` overloads run preflight
   immediately before submission and make no HTTP request after a rejected or
   unavailable result.
3. The v1alpha1 project blueprint accepts authenticated-map collections,
   encodings, authorization/bounds, and inline CDDL schemas. Rendering compiles
   source CDDL to canonical schema IR, constructs canonical genesis, emits the
   state commitment identity, and writes
   `config/authenticated-map-genesis.hex`.
4. Project initialization exposes a bundled `authenticated-map` recipe. It
   requires all public genesis member keys; devtools never invent membership
   placeholders for a consensus identity.
5. Doctor has an explicit `authenticated-map-schema-encoding` check and names
   collections that combine a schema with `opaque` encoding.
6. The Quarkus/config bridge now forwards the framework-owned `state.*`
   namespace. The exact profile, fingerprint, and genesis-id fields are
   registered as consensus-shared, new-chain-required configuration rather
   than being dropped before provider startup.
7. The user guide documents opaque, canonical-CBOR, schema, and custom plugin
   options; CLI and Java preflight; plugin trust and digest pinning; error
   codes; and the v1 new-chain requirement for validator changes.

## Deliberate boundaries

- Preflight is advisory. Authoritative validation remains in state-machine
  apply on every member.
- The blueprint path supports declarative schemas. It does not imply that an
  arbitrary Java plugin is safe or installed; custom validator descriptors
  remain a programmatic, reviewed genesis path.
- Java validator code is trusted and not sandboxed. The SPI denies state and
  service handles, while operations still require code review, explicit
  allow-listing, conformance evidence, and exact artifact-closure pinning.
- Poseidon JMT remains unavailable with ADR-025 Phase 4 deferred.
- AdmissionPolicy and governed validator evolution remain out of scope.

## Verification

The Phase D suite covers:

- opaque, canonical-CBOR, schema, unknown-collection, and collection-bound
  preflight outcomes;
- explicit plugin `UNAVAILABLE`, custom adapter acceptance/rejection, and
  propagation of adapter failures;
- ordered batch failure and zero HTTP submissions after local failure;
- CLI validation, validator/digest inspection, and code explanation;
- blueprint schema compilation, canonical genesis/settings generation,
  generated genesis/documentation files, and required real membership;
- the named doctor failure for schema-with-opaque configuration;
- `state.*` parity across the shared parser, configuration registry, and
  Quarkus multi-chain adapter; and
- release catalog, acceptance evidence, documentation, metadata digests, and
  packaged runtime regression gates.
