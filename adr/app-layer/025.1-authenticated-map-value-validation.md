# ADR-025.1: Authenticated Map Value Validation — Canonical Encoding, Declarative Schemas, and Validator Plugins

## Status

Accepted — implementation in progress. Phase A (canonical value encoding) is
implemented and qualified; Phases B through D remain to be completed.

This ADR is a pre-release amendment to the `authenticated-map` v1 contract
frozen in
[ADR-025 Phase 0](025-phase-0-contract-measurement-and-dependency-gates.md).
If accepted before the first public release or chain genesis, v1 is reopened,
its genesis codec version and golden vectors are regenerated, and the amended
contract is frozen again. It is never valid to reinterpret an already published
v1 genesis. If that release boundary has been crossed, this decision must ship
as `authenticated-map` v2 instead.

The amendment adds optional, genesis-bound value validation. It does not change
the commitment profiles, operation catalog, authorization subset, consensus
algorithm or finality protocol, or proof format. It also does not introduce
node-local admission policies.

## 0. In plain words

The `authenticated-map` state machine currently treats every value as opaque
bytes with only a length bound. `CollectionDescriptor` in
`AuthenticatedMapContract` is `(id, authorization, restoreAllowed, maxKeyBytes,
maxValueBytes)` — there is no slot for a value encoding or a schema, even though
ADR-025 §3.2's illustrative configuration shows a per-collection `value-format`.

That means the chain authenticates *bytes*, not *records*. Any admitted writer
can commit a malformed value, and once committed it is finalized, replicated,
anchored, and provable. In an authenticated store, a bad write is not merely
wrong — it is permanently enshrined with a valid inclusion proof.

This ADR adds two independent, optional per-collection settings:

1. an **encoding constraint** — `opaque` or `canonical-cbor`; and
2. a **consensus value validator** — `none`, `schema`, or `plugin`.

The default is `valueEncoding = opaque` and `validator = none`, which preserves
the current behavior. A collection opts into canonical encoding, one declarative
schema validator, or one custom validator plugin through the chain blueprint
that produces canonical genesis. These are not mutable node settings.

A schema is authored through a closed CDDL subset and compiled into a versioned,
canonical validation representation before genesis is finalized. A custom
validator is a pure predicate over `(collection, key, value)` whose artifact
closure digest, contract version, and canonical parameters are pinned in
genesis. Schema and plugin validators are mutually exclusive in v1; either may
be combined with the independent canonical-CBOR encoding constraint.

Anything requiring reads of other keys stays out of scope and belongs in a
composite component or a custom state machine.

Every setting is optional per collection, declared in genesis, and contributes
to the genesis identity and format fingerprint. The same deterministic check is
used during proposal pre-validation and authoritative application. Client-side
preflight may reuse it for developer experience, but is not a validity boundary.
Node-local admission or business-policy hooks are outside this ADR.

## 1. Problem

### 1.1 Values are opaque in the frozen v1 contract

`AuthenticatedMapContract.CollectionDescriptor` carries no value-format field.
Phase 0 recorded the consequence explicitly: "opaque value bytes, with
application-specific canonical codecs enforced by the owning application before
command construction."

Enforcement by the client is enforcement by the party with the least incentive to
be careful and the most incentive to cut corners. It is also unverifiable: a
proof consumer cannot tell whether a value was ever checked.

### 1.2 Non-canonical encodings are a live correctness gap, independent of schemas

Two clients can commit semantically identical CBOR records with different byte
encodings — different map key ordering, non-minimal integer widths, indefinite
length forms. Today both are accepted.

The consequences are concrete:

- `logicalValueHash` differs for semantically identical records, so
  `COMPARE_AND_SET` bound to an expected value hash is fragile across producers;
- the state root differs for logically identical state, which weakens any claim
  that two independent producers writing the same fact converge; and
- the canonical-decode discipline applied to every other codec in this codebase
  (`AppBlockCodec`, `EffectRecord`, `RoleWorkflowCbor`, `CompositeProfileCodec`,
  and the authenticated-map codecs themselves) stops precisely at the value
  boundary.

This is worth closing even for deployments that never declare a schema.

### 1.3 The gap between configuration and a custom state machine is too wide

Today an application that needs one field check must either accept unvalidated
values or write a full custom state machine, reimplementing or wrapping
collections, revisions, compare-and-set, controller transfer, revocation,
batches, receipts, and proofs.

That cliff pushes teams toward the unvalidated option, which is the outcome this
ADR exists to prevent.

### 1.4 Proof semantics are weaker than they need to be

With opaque values, a verifier proves "these bytes were committed at this height
under this root." With a genesis-declared schema, a verifier that also checks the
chain identity and validation profile can rely on the stronger statement "a
record conforming to schema S, with field X equal to Y, was committed." The
second statement is what makes the product an authenticated *registry* rather
than an authenticated blob store.

### 1.5 Future ZK statements need a typed field layout

ADR-025 §9.2 anticipates ZeroJ circuits proving application statements about map
entries. A circuit that must assert `status = ACTIVE` or `balance >= X` needs a
known, canonical field layout to index into. Against opaque bytes every such
statement requires a bespoke circuit per application encoding.

A frozen declarative schema supplies that layout as a by-product. Validation is
therefore closer to a prerequisite for the ZK path than to a developer
convenience.

### 1.6 Timing

Phase 0 has frozen the genesis codec, `CollectionDescriptor`, and their cross-
language golden vectors in the repository. If the public v1 release/genesis
boundary has not been crossed, reopening them now costs a deliberate codec bump
and vector regeneration. After that boundary, the same change requires v2, a
compatibility path, and a migration story.

## 2. Decision summary

1. Add optional per-collection **value encoding** enforcement. The initial
   catalog is `opaque` (the default and current behavior) and
   `canonical-cbor`.
2. Add an optional per-collection **consensus value validator**. The initial
   selection is `none` (the default), one declarative schema, or one custom
   validator plugin.
3. Compile the supported CDDL authoring subset into canonical
   `yano-cbor-schema-ir-v1` bytes before genesis. Canonical IR bytes, not parser-
   dependent source evaluation, determine the verdict.
4. Pin a plugin validator's provider id, artifact-closure digest, SPI contract
   version, and canonical parameter bytes in genesis. Plugin parameters never
   come from node-local configuration.
5. Declare validators in a canonically ordered, bounded genesis `validators`
   list. Collections reference a validator by id, so several collections may
   share one.
6. Make every validation setting part of canonical genesis bytes, `genesisId`,
   and the format fingerprint. A node whose resolved settings differ fails
   before consensus participation.
7. Make validation a **pure function of `(collectionId, applicationKey, value)`**.
   Validators receive no state reader, sender, height, block, emitter, clock,
   ambient configuration, or I/O service.
8. Invoke validation only for value-bearing mutations that produce an `ACTIVE`
   entry. Tombstones, controller transfers, and revocations are not validated.
9. Represent an ordinary validation rejection as a deterministic typed verdict.
   Unexpected plugin or host failures are node failures, not user rejections;
   the implementation must not convert arbitrary `Throwable` instances into a
   consensus verdict.
10. Invoke the same consensus validator during proposal pre-validation and
    authoritative `apply`. The validator's verdict is state-independent and
    must be identical at both call sites.
11. Require genesis initial entries to satisfy their collection's encoding and
    validation rules during genesis construction.
12. Keep validators **immutable for the chain generation in v1**, exactly as the
    commitment profile is. Governed, height-activated validator evolution is
    deferred to a follow-up ADR.
13. Keep validation that reads other keys, collections, membership, or role
    state out of this mechanism. That is composite or custom state-machine
    territory.
14. Do not add an `AdmissionPolicy` or generic all-state-machine validation
    framework. Those are separate decisions if they are ever needed.

## 3. Non-negotiable rules

These follow from ADR-024's reviewed failure classes and are not negotiable
during implementation.

**R1 — Consensus-critical, therefore genesis-bound.** A validation setting that
differs between members causes the same command to be accepted by one node and
rejected by another, producing divergent state roots with no diagnostic. Every
setting in this ADR is part of canonical genesis bytes and the format
fingerprint. A node whose resolved genesis does not match refuses to start and
never adopts a retained store.

**R2 — Deterministic or it does not ship.** A validator must produce byte-identical
verdicts for identical inputs, on every member, on every supported JVM, across
restarts, and under replay. Sources of nondeterminism explicitly prohibited:
wall clock, randomness, I/O, network, filesystem, environment or system-property
reads, locale-sensitive comparison, default charset, unordered collection
iteration reaching a verdict, ambient classpath discovery, and dependency-
sensitive behavior.

**R3 — Total by contract; host failures are not verdicts.** Validation is total
over all byte inputs within declared bounds and returns an explicit typed verdict.
A conforming validator does not throw for malformed input. If trusted in-process
plugin code unexpectedly throws or the JVM reports a resource/fatal failure, the
affected node fails closed and stops consensus participation. The runtime must
not catch arbitrary `Throwable` instances and commit a rejection that another
node may not produce.

**R4 — Deterministically bounded work.** Validation cost is bounded by value,
schema, parameter, nesting, and evaluation-step limits. Backtracking regular
expressions, unbounded recursion, and unbounded allocation are prohibited.
Wall-clock timeout is useful for conformance measurements and operations, but
must never determine a consensus verdict. A future sandbox may use a deterministic
instruction or fuel limit.

**R5 — Pure, state-free.** A validator cannot read chain state. This keeps its
pre-validation and application verdicts trivially consistent, keeps the
mechanism composable with future backends, and prevents the hook from silently
becoming a second, weaker state-machine SPI that bypasses the conformance gates.

**R6 — Trust is explicit.** A Java interface and restricted initialization
context do not sandbox Java bytecode: plugin code can still call JDK filesystem,
network, clock, process, reflection, or thread APIs directly. Consequently v1
Java validators are trusted, operator-approved consensus code, comparable to a
custom state machine. Digest pinning proves which code was selected; conformance
testing provides evidence about it; neither makes hostile code safe. Loading
untrusted validators is deferred until a deterministic, metered sandbox exists.

## 4. Validation model and the dividing line

| Mechanism | Declared as | Typical use |
|---|---|---|
| Encoding constraint | `valueEncoding` on the collection | Optional rejection of non-canonical CBOR |
| Declarative schema | Genesis-inline canonical IR | Field structure and bounds |
| Custom validator | Pinned artifact closure and parameters | Self-contained domain rules |
| Composite or custom machine | Outside this ADR | Rules that read other state |

**The dividing line is that a value validator sees only
`(collectionId, applicationKey, value)`.** The moment a rule needs to read
another key, it is a state transition rule, not a value predicate, and it must be
written as a composite component under ADR-013.2 where the determinism contract,
namespace isolation, effect quotas, and conformance harness already apply.

Implementers must resist requests to "just pass the state reader" into a
validator. That single parameter would convert a bounded, testable predicate into
an unconstrained second state-machine surface without any of the accompanying
guarantees.

## 5. Encoding constraint — canonical value encoding

### 5.1 Catalog

```text
VALUE_ENCODING_OPAQUE         = 0   // current behavior, no encoding constraint
VALUE_ENCODING_CANONICAL_CBOR = 1   // value must be one canonical CBOR item
```

The catalog is closed and versioned, in the same style as
`StateCommitmentProfiles`. Adding an encoding is a contract revision with new
golden vectors.

### 5.2 Canonical CBOR definition

`canonical-cbor` requires all of:

- exactly one top-level CBOR data item consuming the entire value, no trailing
  bytes;
- definite-length encoding for all strings, arrays, and maps;
- minimal-length integer and length encodings;
- map keys sorted by canonical byte order with no duplicates;
- no undefined, no unassigned simple values, no floating-point NaN payload
  variance, and no tags outside a declared allow-list (empty in v1);
- a maximum nesting depth of 32, at most 65,536 decoded items, and at most
  65,536 entries in any one container, in addition to the collection's frozen
  byte bound.

Enforcement uses a bounded, allocation-light deterministic-CBOR scanner over the
original bytes. This is stricter and cheaper than constructing an unbounded
object graph and makes preferred floating-point width, strict UTF-8, and encoded
map-key order explicit. The scanner is a contracts-internal shared primitive for
the authenticated-map value and schema paths; it is independently exercised by
the checked-in conformance corpus.

### 5.3 Interaction with tombstones and hashes

A `REVOKED` entry carries a canonical empty tombstone value
(`AuthenticatedMapContract` already enforces `value.length == 0` for
`STATUS_REVOKED`). Encoding rules apply only to values of `ACTIVE` entries.
`logicalValueHash` is unchanged: it remains the domain-separated Blake2b-256 of
the value bytes, computed after the encoding check passes.

## 6. Declarative schema validator

### 6.1 Authoring language and canonical representation

The developer-facing authoring language is a **closed subset of CDDL (RFC
8610)**, identified by:

```text
cddl-yano-subset-v1
```

CDDL is chosen because it is CBOR-native, matching the canonical encoding of the
rest of this codebase, and because `core-api/src/main/cddl` and the existing CDDL
cross-validation gate already establish it in the project.

CDDL text is not interpreted independently by every consensus member. Devtools
compile the accepted subset into canonical CBOR validation IR identified by:

```text
yano-cbor-schema-ir-v1
```

The IR has a closed node catalog, explicit numeric bounds, canonical ordering,
one root, and no extension or implementation-defined nodes. Genesis commits the
IR bytes and its catalog id. Nodes evaluate those bytes directly. The source CDDL
may remain in a blueprint or source bundle for developer inspection, but it does
not determine consensus after genesis is finalized. Two independent compilers
must produce the same IR golden vectors before the schema phase ships.

The subset **must exclude**, and the loader must reject:

- `.regexp` and any control operator delegating to a host regular-expression
  engine;
- sockets, generics, and any construct requiring unbounded unification;
- external references or includes of any kind;
- unbounded repetition without an explicit upper bound; and
- any construct whose evaluation cost is not bounded by (value size × schema
  size).

Permitted authoring constructs are: named rules, struct/map and array definitions,
primitive types (`uint`, `nint`, `int`, `tstr`, `bstr`, `bool`, `null`), size and
range control (`.size`, `.lt`, `.le`, `.gt`, `.ge`, `.eq`), literal values,
enumerated choices, optional (`?`) and required occurrence with explicit bounds,
and a single declared root rule.

JSON Schema is explicitly rejected as the v1 language; see §13.A.

### 6.2 Schema declaration

Canonical schema IR bytes are inlined in genesis rather than referenced by
digest and distributed out of band. Schemas are small, a node must be able to
evaluate them, and inlining removes a distribution failure mode. Canonical IR is
bounded at 64 KiB per schema. Authoring-source size is a devtools concern and is
not part of the runtime contract.

### 6.3 Evaluation semantics

- The schema is evaluated against the decoded canonical CBOR item. A collection
  declaring a schema validator **must** declare `valueEncoding = canonical-cbor`;
  genesis construction rejects the combination of a schema with `opaque`.
- Evaluation is total: every input either conforms or does not. CDDL compilation
  and canonical-IR validation happen before genesis finalization. A runtime that
  cannot decode the declared IR catalog fails startup before consensus
  participation.
- The consensus verdict is typed `ACCEPT` or `REJECT`. Diagnostic detail may be
  surfaced to the submitting client through the local API but **must not** enter
  state, the receipt result commitment, or the state root, because free-form
  diagnostic text is a determinism hazard.

## 7. Custom validator plugin

### 7.1 Module boundary

`ValidatorDescriptor` is part of the authenticated-map genesis and wire
contract. It belongs beside `CollectionDescriptor` in
`appchain-stdlib-contracts`, preferably as
`AuthenticatedMapContract.ValidatorDescriptor`; it does not belong in
`core-api`.

The Java validator SPI has a different role: it is a host-loaded, published
ServiceLoader contract. Every currently catalog-supported contribution SPI lives
in `core-api`, and `plugin-catalog` deliberately obtains those types through its
existing `core-api` dependency. The validator SPI therefore belongs in
`core-api`, under an explicitly authenticated-map-specific package such as
`com.bloxbean.cardano.yano.api.appchain.authmap`. Its type names remain
`AuthenticatedMap...`; this does not create a generic validator mechanism for
other state machines.

`core-api` must not depend on `appchain-stdlib-contracts`. Consequently the SPI
uses only JDK types and its own small API records; it does not expose
`CollectionDescriptor`. `plugin-catalog` adds an `authenticated-map-validator`
contribution kind using the new SPI through the dependency it already has. The
contracts artifact preserves its enforced rule that it contains wire/state
contracts but no ServiceLoader registrations or SPI types.

### 7.2 SPI shape

```java
public interface AuthenticatedMapValueValidator {
    ValidatorVerdict validate(
            String collectionId,
            byte[] applicationKey,
            byte[] value
    );
}

public interface AuthenticatedMapValueValidatorFactory {
    String id();
    String contractVersion();
    AuthenticatedMapValueValidator create(ValidatorInitContext context);
}

public enum ValidatorVerdict {
    ACCEPT,
    REJECT
}
```

The parameter list is the contract. There is deliberately no state reader, no
sender, no height, no `AppBlock`, no emitter, and no context object that could
later grow one. `applicationKey` is supplied because binding a value field to its
key (for example, requiring an embedded serial to equal the key) is a common,
still-pure constraint.

`ValidatorInitContext` supplies only the descriptor id, provider id, pinned
contract version, canonical genesis parameter bytes, and canonically ordered ids
of the collections bound to it. It does not expose `CollectionDescriptor` or
supply chain state, node configuration, services, schedulers, logging callbacks,
or a class-loader escape hatch. Bounds and encoding are host-enforced before the
plugin is called. Parameters are bounded canonical CBOR and are defensively
copied before plugin construction.

The factory creates one fresh validator per chain and validator descriptor during
startup. The returned validator must be immutable or thread-safe because
pre-validation may be concurrent with other pre-validation. The host defensively
copies mutable byte-array inputs before invoking plugin code, and a plugin cannot
retain a reference that later affects command decoding or state application.

Discovery is by `ServiceLoader` through the existing plugin catalog, so validator
bundles are inspected, correlated, and digested by the same machinery as state
machine and effect executor bundles.

The narrow context is an API boundary, not a Java security boundary. Implementors
remain subject to R2 and R6 even though Java code can bypass the context and call
JDK APIs directly.

### 7.3 Pinning

`ValidatorDescriptor.definition` for a plugin validator is the 32-byte
artifact-closure digest computed by the plugin catalog. Its contract version and
canonical parameters are separate descriptor fields. At startup the runtime
resolves the validator bundle, recomputes the closure digest, matches the factory
provider id and contract version, and **fails closed** on any mismatch. Descriptor
instance ids and provider ids are separate so one factory may be instantiated
with different genesis-bound parameters under several descriptor ids.

This makes ADR-024's catalog-provenance finding a blocking dependency rather than
an improvement: `PluginCatalogInspectionPolicy` currently records digests but
never enforces them, so allow-listing is by self-asserted bundle id. Custom
validator plugins must not ship until digest pinning is enforced, because
otherwise a rogue artifact declaring the same bundle id silently supplies the
consensus-critical predicate.

### 7.4 Trust and determinism gate

A v1 Java validator bundle is trusted application consensus code. It is not
loadable in a production profile until operators explicitly allow it and it
passes a conformance suite that:

- runs a fixed corpus of conforming, non-conforming, boundary-sized, non-canonical,
  and adversarial values;
- asserts byte-identical verdict vectors across two independent runs;
- asserts identical results under concurrent and reordered invocations;
- asserts byte-identical verdict vectors across two **isolated class loaders**
  with deliberately differing optional dependencies present, which is the check
  that would have caught the ambient-Jackson-module class of defect;
- asserts no exception escapes for any corpus input, including truncated and
  oversized values; and
- asserts a bounded evaluation-step/input envelope and measures time and
  allocation as release evidence, without using wall-clock time as a verdict.

The conformance fixture must itself include a deliberately nondeterministic
validator that the harness is required to fail, so the gate is proven to work
rather than assumed to.

This gate detects known failure classes but cannot prove arbitrary Java bytecode
safe or deterministic. Untrusted third-party validator execution requires a
follow-up deterministic sandbox contract with no host I/O imports and a metered
instruction budget. It is not enabled by this ADR.

## 8. Contract changes to ADR-025

### 8.1 `CollectionDescriptor`

```text
CollectionDescriptor(
    String  id,
    int     authorization,
    boolean restoreAllowed,
    int     maxKeyBytes,
    int     maxValueBytes,
    int     valueEncoding,     // NEW: closed catalog, default VALUE_ENCODING_OPAQUE
    String  validatorId        // NEW: empty string = no consensus value validator
)
```

`validatorId`, when non-empty, must resolve to exactly one entry in
`Genesis.validators`. Canonical encoding places the new fields after the existing
ones; the genesis codec version increments. A collection selects at most one
schema or plugin validator in v1. The independent encoding constraint is applied
before that validator.

### 8.2 `Genesis`

```text
Genesis(
    String chainId,
    String commitmentProfileId,
    byte[] formatFingerprint,
    byte[] frameworkConsensusProfileDigest,
    byte[] membershipCommitment,
    byte[] anchorPolicyCommitment,
    int    maxBatchItems,
    int    maxBatchBytes,
    List<CollectionDescriptor> collections,
    List<ValidatorDescriptor>  validators,     // NEW, canonically ordered by id
    List<GenesisEntry>         initialEntries
)

ValidatorDescriptor(
    String id,               // canonical lowercase ASCII, unique, <= 64 bytes
    int    kind,             // VALIDATOR_KIND_SCHEMA = 0 | VALIDATOR_KIND_PLUGIN = 1
    String providerId,       // empty for schema; plugin factory selector otherwise
    String contractVersion,  // schema IR catalog or validator SPI contract version
    byte[] definition,       // canonical schema IR or 32-byte artifact-closure digest
    byte[] parameters        // canonical CBOR map; empty map for schemas; <= 16 KiB
)
```

Bounds: at most 32 validators per genesis; validator ids canonically ordered and
unique; unreferenced validators rejected at construction. `definition` is bounded
at 64 KiB for schemas and exactly 32 bytes for plugins. Parameters are canonical,
definite-length CBOR maps with text keys in canonical order and no duplicate
keys. All descriptor fields contribute to canonical genesis bytes, `genesisId`,
and the format fingerprint.

For a schema descriptor, `providerId` is empty,
`contractVersion = yano-cbor-schema-ir-v1`, `definition` is canonical IR, and
`parameters` is the canonical empty map. For a plugin descriptor, `providerId`
is the exact `AuthenticatedMapValueValidatorFactory.id()`, `contractVersion`
matches the factory contract, `definition` is the artifact-closure digest, and
`parameters` initializes that descriptor instance. Multiple descriptor ids may
therefore use the same provider with different genesis-bound parameters.

The Java record for `ValidatorDescriptor` lives in
`appchain-stdlib-contracts`, not `core-api`; see §7.1.

### 8.3 Error codes

Existing codes occupy 0 through 9 (`ERROR_NONE` through
`ERROR_RESTORE_FORBIDDEN`). This ADR adds:

```text
ERROR_VALUE_ENCODING  = 10   // value is not canonical under the declared encoding
ERROR_VALUE_SCHEMA    = 11   // value failed the declarative schema
ERROR_VALUE_VALIDATOR = 12   // validator plugin returned REJECT
```

When a message reaches authoritative application, codes enter the receipt and
result commitment exactly as existing codes do. A request rejected before block
inclusion receives a typed local API response but cannot have an authenticated
receipt; §9 defines the distinction.

### 8.4 Invocation points

Validation runs on the mutations that produce an `ACTIVE` entry value:
`PUT`, `PUT_IF_ABSENT`, `COMPARE_AND_SET`, and `RESTORE` when it carries a value.
It does **not** run for `TRANSFER_CONTROLLER` (no value change) or `REVOKE`
(canonical empty tombstone).

Within `BATCH`, each item is validated independently, and any failure fails the
whole batch atomically under the existing all-or-nothing rule.

Consensus ordering within a single mutation is frozen and tested. It is: envelope
and structural checks, collection bounds, authorization and operation
preconditions, encoding constraint, schema or plugin verdict, then the state
transition. This avoids spending the more expensive validation budget for an
unauthorized or already-invalid transition and prevents validation diagnostics
from becoming an authorization oracle.

### 8.5 Genesis initial entries

`GenesisEntry` values are subject to the same encoding and validation rules as
runtime mutations, checked during genesis construction. A genesis whose initial
entries violate their own collection's declared rules is invalid and must not be
constructible.

### 8.6 Contract versioning

Acceptance before the first public v1 release reopens the Phase 0 contract,
increments the genesis codec version, regenerates every Java and independent
golden vector, and re-freezes v1. No decoder may silently assign defaults while
decoding bytes bearing the old codec version. If a v1 artifact or genesis has
already been published as stable, the fields in this section define v2 instead.
Historical genesis bytes and ids are never reinterpreted.

## 9. Consensus pre-validation and authoritative application

`AuthenticatedMapStateMachine.validate(AppMessage)` performs structural and
bounds checks today, and `validateForBlock` layers state-dependent checks on top.
The implementation may perform encoding and value validation early in
`validate`, because those predicates are state-independent, and repeats them in
the authoritative mutation path in `apply`. `validateForBlock` continues to own
state- and height-dependent proposal-selection checks.

This yields a property worth stating precisely: the **consensus value validator's
verdict** cannot differ between pre-validation and application for the same
genesis-bound validator and input. The complete proposal-admission result may
still differ because it includes state, height, authorization, duplication, and
pool conditions. The state-independent property is a direct consequence of R5
and is lost the moment a state reader is added.

A request rejected by a gateway, client preflight, mempool, or proposal builder
is not included in a block and therefore has no authenticated rejection receipt.
It receives a bounded typed local response. If a value-bearing message reaches
`apply`, the same validator runs authoritatively; a normal `REJECT` follows the
existing deterministic rejected-receipt path. An unexpected in-process plugin or
host failure follows R3 and fails the affected node closed instead of inventing a
user rejection.

This section does not define an operator-configurable `AdmissionPolicy`.
Client-side validation in Phase D is an optimization and developer-experience
feature only. Neither can substitute for the authoritative check in `apply`.

## 10. Immutability and the replay invariant

**Invariant RI-1: a validation verdict must be a pure function of the genesis-
declared validator and the input. It must never change for a given chain
generation.**

If tightening a rule could retroactively invalidate a historical block, catch-up
and replay from genesis would fail and a fresh member could never join. This
invariant is what makes replay safe, and it must survive any future evolution
mechanism.

In v1 the invariant is satisfied structurally: validators live in immutable
genesis, so there is no evolution within a chain generation. Changing a validator
requires the same path ADR-025 §5.3 defines for the commitment profile — a new
chain generation importing a canonically exported snapshot and linking to the old
chain's final checkpoint.

**Practical guidance that must appear in the product documentation.** Because v1
validators are immutable for the life of the chain, they suit stable,
standards-derived record shapes — GS1 identifiers, W3C VC status entries, LEI
records, certificate references. For record shapes expected to evolve, either use
only an encoding constraint with no validator until governed evolution exists,
or accept a new chain generation. Teams should not discover this after committing
a five-year registry to a schema they outgrow in eight months.

**Deferred to a follow-up ADR (025.2).** Governed, height-activated validator
evolution following the ADR-015 pattern: a height→validator table in authenticated
state, validation applied at write time against the validator active at that
height, prior entries never re-validated, and the whole table committed and
verified per block. The descriptor layout in §8 is designed so that adding a
height dimension later does not require a second genesis revision.

## 11. Non-goals

This mechanism is not:

- a rule engine, a workflow engine, or a place for business logic;
- an operator-configurable `AdmissionPolicy` or node-local preflight framework;
- a generic validator extension point for every state machine;
- a cross-key or cross-collection integrity mechanism;
- an authorization mechanism — that remains the collection policy's job, and
  validators deliberately cannot see the sender;
- a sandbox for untrusted Java plugins;
- a way to make values confidential;
- a guarantee that a well-formed record is *true*; or
- a substitute for the composite programming model.

Validation constrains encoding, shape, and self-contained value invariants. It
does not establish external truth or relationships with other state.

## 12. Security and operational requirements

- CDDL compilation happens before genesis finalization. At startup, a node
  canonically decodes and validates the committed schema IR once; failure is
  fatal, so no compilation cost or parser variance exists on the hot path.
- Validator invocation is bounded by deterministic input, nesting, parameter,
  schema, and evaluation-step limits. The runtime records per-collection
  validation counters, rejection-by-code counters, latency, and allocation
  observations outside consensus. Operational timing never changes a verdict.
- Validator diagnostic strings never enter state, receipts, or roots.
- The resolved validator set — descriptor ids, kinds, provider ids, contract
  versions, definition digests, parameter digests, and plugin artifact-closure
  digests — appears in the status surface, snapshot manifests, evidence bundles,
  and identity document, so cross-node parity is inspectable rather than assumed.
- A node that cannot resolve a genesis-declared validator, or that resolves one
  whose id, contract version, or digest differs, fails closed before consensus
  participation.
- Production configuration accepts Java validator bundles only as trusted,
  explicitly allow-listed application consensus code. It must not describe them
  as sandboxed or safe for hostile third-party code.

## 13. Alternatives considered

**A. JSON Schema as the authoring language.** Rejected. `$ref` invites external
resolution, `pattern` delegates to an implementation-dependent regular-expression
engine with catastrophic-backtracking exposure, and `format` assertion behavior
varies between implementations. Each is a nondeterminism or unbounded-work hazard
inside the consensus path. A heavily subsetted JSON Schema would be no smaller a
specification than the CDDL subset and would fit the CBOR-native codebase worse.

**B. Node-local configuration as the authoritative validator.** Rejected
outright. It is the exact silent-fork mechanism ADR-024 documented: nodes
disagree on whether an applied command is valid, and roots diverge. A stricter
node-local prefilter could be advisory without changing consensus, but this ADR
does not add or rely on one.

**C. Validate on read in the client only.** Retained as a legitimate lighter
option for single-writer registries, and worth documenting as such: commit the
schema digest in genesis, have values carry a schema id, and let readers reject
non-conforming records. Consensus risk is zero; the cost is that bad data is still
permanently committed and provable. The rule of thumb for choosing: **validate in
consensus when a bad write harms someone other than the writer.** Consortium
registries whose members act on each other's records need in-consensus
validation; a registry where only the writer relies on the data does not.

**D. Require a custom state machine for any validation.** Rejected as the sole
answer. It is correct for cross-key rules and remains the answer for those, but
forcing a full machine for a single field check drives teams to skip validation
entirely, which is the outcome this ADR exists to prevent.

**E. Pass a state reader to validators.** Rejected. It would break the
pre-validation/application verdict equivalence in §9, make validators a second
state-machine SPI without the conformance and isolation guarantees, and
reintroduce the cross-key atomicity questions that ADR-013.2 already answers.

**F. Ship the plugin hook before digest pinning is enforced.** Rejected. Without
enforced pinning, the consensus-critical predicate is selected by a self-asserted
bundle id, so an operator's allow-list provides no cryptographic protection.
Declarative schemas can ship first because inline canonical IR is self-pinning
through the genesis digest.

**G. Put descriptor and SPI in the same artifact.** Rejected. The descriptor is
a versioned authenticated-map genesis/wire contract and belongs in the no-SPI
contracts artifact. The SPI is a catalog-supported host extension and follows
the existing public SPI boundary in `core-api`. Keeping the split avoids making
the plugin catalog depend on a product contracts artifact while preventing a
product genesis record from becoming a generic framework model.

## 14. Implementation plan

Sequenced so each phase is independently valuable and independently gated.

**Phase A — Canonical value encoding.**

1. Add `valueEncoding` to `CollectionDescriptor` and bump the genesis codec
   version; regenerate cross-language golden vectors.
2. Implement canonical-CBOR enforcement through the shared strict-decode helper.
3. Add `ERROR_VALUE_ENCODING`, wire it into receipts and the result commitment.
4. Enforce the rule for genesis initial entries.
5. Tests: non-canonical map ordering, non-minimal integers, indefinite lengths,
   trailing bytes, the round-trip equality property, and unchanged mutation
   semantics for the explicit `opaque` default; determinism across restart,
   snapshot restore, and catch-up.

**Phase B — Declarative schema.**

1. Freeze `cddl-yano-subset-v1`, its rejected-construct list, and
   `yano-cbor-schema-ir-v1`; publish compiler and evaluator golden vectors
   verified by Java and one independent implementation.
2. Add `ValidatorDescriptor`, the genesis `validators` list, `validatorId` on the
   collection, and `ERROR_VALUE_SCHEMA`.
3. Implement devtools compile-before-genesis, startup canonical-IR validation,
   and deterministically bounded runtime evaluation.
4. Tests: conformance corpus, boundary sizes, adversarial nesting, multi-member
   identical-root replay, and a two-member mismatched-genesis test asserting
   fail-closed startup rather than divergence.

**Phase C — Custom validator plugin.** Blocked on enforced artifact-closure
digest pinning and acceptance of the trusted-code deployment policy in §7.4.

1. Add the narrowly named SPI and typed verdict to `core-api`, add the
   `authenticated-map-validator` catalog contribution, and implement canonical
   parameter handling, production allow-listing, and digest-pinned resolution.
2. Build the determinism conformance harness including the two-class-loader check
   and deliberately nondeterministic validator the harness must fail. Verify that
   unexpected plugin/host failures fail the node closed and never become receipts.
3. Ship one first-party reference validator — a standards-derived identifier
   check is the natural candidate — as a worked example and as harness input.

**Phase D — Developer experience.**
1. `appchain` CLI: validate a candidate value against a chain's declared schema
   offline; inspect the resolved validator set and digests; explain a rejection
   code.
2. Client-side preflight so applications fail locally before submitting, clearly
   identified as non-authoritative.
3. Devtools blueprint support for declaring collections with encodings and
   schemas, and doctor checks for the schema-with-opaque-encoding mistake.

**Deferred — ADR-025.2.** Governed height-activated validator evolution, per §10.

## 15. Verification and acceptance criteria

**Compatibility.** A collection declaring `valueEncoding = opaque` and no
validator has the same mutation acceptance and value semantics as the pre-ADR
contract. Genesis bytes, `genesisId`, the genesis marker, and roots that include
that marker are intentionally versioned and may differ. Every command, entry,
query, receipt, and proof encoding not amended by §8 remains byte-identical. If
this ships as v2, existing v1 decoding and behavior remain available unchanged.

**Determinism.** Two members with identical genesis produce identical roots over a
corpus that includes conforming, non-conforming, boundary, and adversarial values.
Replay from genesis, restart, snapshot restore, and catch-up all reproduce the
same roots and the same receipts.

**Fail-closed.** Two members with genesis differing only in a validation setting
fail to form a chain, with a startup diagnostic naming the mismatched field —
never a divergent root.

**Totality and failure classification.** No corpus input, including truncated,
oversized, deeply nested, and non-canonical values, causes the built-in encoding
or schema evaluators, or a conforming plugin, to escape normal verdict handling.
Tests also prove that an unexpected plugin or host failure fails the node closed
and cannot be committed as a user rejection.

**Receipts.** A validation rejection reached during authoritative application
yields a retrievable authenticated receipt whose error code identifies the
failing mechanism and whose result commitment is stable across nodes. A request
rejected before inclusion yields only the bounded typed local response specified
in §9; tests must not claim it has an authenticated receipt.

**Bounds.** Validation adds bounded, measured cost per value; the Phase 0
benchmark dimensions are re-run with a representative schema and the delta is
published rather than asserted.

## 16. Consequences

**Positive.** Several use cases move from "requires a custom state machine" to
"configuration only," which is the core product claim of the authenticated-map
product. Proofs carry a stronger statement. Non-canonical value encodings — a
correctness gap independent of schemas — are closed. Future ZK circuits gain a
typed field layout. Rejections that reach authoritative application become
authenticated evidence, while pre-inclusion failures remain inexpensive.

**Negative.** The consensus-critical surface grows: every validation setting is
now something that must be identical across members, versioned, and migration-
planned. The Java plugin path introduces trusted application code into `apply`;
digest pinning and conformance reduce but do not eliminate that risk. v1
immutability means a schema mistake is expensive to correct, which raises the
cost of the initial modeling decision. Genesis grows by the inlined schema IR and
plugin parameter bytes. The public `core-api` gains one narrowly scoped
authenticated-map plugin SPI and must preserve its compatibility once published.

**Neutral but worth stating.** This ADR does not make the map a database.
Single-value validation is not relational integrity, and no amount of schema
strictness substitutes for the composite model when rules span keys.

## 17. Open questions

1. Are 64 KiB per schema IR, 16 KiB per canonical parameter map, and 32
   validators the right production bounds after genesis-size and evaluation
   benchmarks?
2. Does the validator set belong in the anchor datum's committed profile, or is
   its presence in `genesisId` and the format fingerprint sufficient?
3. Which first-party reference validator is worth shipping in Phase C?

Each answer that changes canonical bytes, verdicts, or genesis identity requires
this ADR to be amended before the corresponding phase begins.
