# ADR-025.2 Phase B — Authenticated-map composite assembly

## Status

Implemented and qualified on 2026-08-04.

## Assembly delivered

The unchanged `authenticated-map` provider now creates one
`CompositeStateMachine` with machine ID `authenticated-map`. Its component
order is committed as:

```text
domain-actors
role-approvals
authenticated-map
```

The authenticated-map transition and point/receipt query implementation is
isolated behind `AuthenticatedMapComponent`. The final-v1
`authenticated-map-authorization-v1` workflow exclusively owns map command
execution and receives only the declared component views. Workflow order is
now preserved in canonical composite-profile bytes and therefore contributes
to the profile digest instead of being silently sorted by workflow ID.

Basic genesis profiles expose only the map workflow and the existing point and
receipt aliases. Governed genesis profiles additionally expose the actor query
surface, role/policy query surface, actor command topic, and committed
`role-approval-v1` workflow before the map workflow. The Phase-C and Phase-D
processors are deliberately fail-closed with `GOVERNED_ROUTE_UNSUPPORTED`;
copying an artifact or changing local configuration cannot enable them for a
basic genesis.

## Genesis and restart behavior

At height 1, the composite initializes in component order:

1. immutable revision-1 organizations, actors, key-proof-authenticated actor
   records, and administrator authority plus current pointers;
2. direct-role and approval-policy revision-1 records, current pointers, and
   empty approval statistics; and
3. authenticated-map genesis marker and initial entries.

Every component preflights its complete owned closure before writing. The
framework applies all component and workflow writes in the single block-state
transaction. Restart initialization verifies the immutable genesis records,
valid current-pointer encoding, and that each current pointer resolves to a
canonical record with the expected stable ID and revision. A missing,
corrupt, mismatched, or dangling record fails startup.

## Compatibility and validation

`open`, `owner`, and `member` retain their ADR-025 transition rules while using
the final-v1 action/authorization envelope. The public provider rejects the
intermediate legacy command envelope. Point and receipt paths remain available
at their existing external aliases while their physical proof keys are now
composite-namespaced.

Canonical-CBOR encoding, declarative schema validation, custom validator SPI
resolution, initial-entry checks, deterministic validation, and batch atomicity
all execute inside the final workflow. A decodable finalized command that
fails value encoding, schema, plugin validation, or authorization assignment
receives its frozen typed receipt and performs no partial write.

Candidate-height workflow admission is a separate composite hook. Structural
`validate` does not invent height 1, while `validateForBlock` supplies the real
candidate height for `member` checks.
