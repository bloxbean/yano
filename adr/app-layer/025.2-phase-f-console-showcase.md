# ADR-025.2 Phase F — Capability-gated console and showcase

## Status

Implemented and qualified on 2026-08-04.

## Origin and credential prerequisite

The §10.5 gate is closed for every console route. The shared client stores a
credential only as a record bound to its exact normalized API base
(`yano.console.api-credential.v2`); lookup returns a key only for that exact
base, a query-selected or otherwise different base receives no `X-API-Key`,
and the unscoped v1 key is deleted rather than migrated. The node now serves a
Content-Security-Policy header for every `/ui` console page restricting
`connect-src` to `'self'` plus operator-configured origins
(`YANO_CONSOLE_CONNECT_SRC_EXTRA`), with the plugin dashboard keeping its
stricter existing filter. The origin/credential regression suite covers base
normalization, resolution order, exact-base credential binding, fail-closed v1
migration, discovery-document pinning, redirect rejection, and the CSP/header
set served for each packaged page.

Closing the gate surfaced a Phase-E packaging defect: the stdlib bundle
manifested its domain API as `authenticated-map-v1`, which violates the
reverse-DNS contribution rule and had failed `:app:generatePluginCatalogIndex`
since the Phase-E merge. The contribution now uses the bundle id, and the
packaged-catalog test asserts the stdlib and role-workflow domain APIs are
both activated through the declared bundle dependency.

## Capability discovery and route identity

The generic app-chain page shows an `Authenticated Map` link only when the
selected chain reports `stateMachine = authenticated-map`. The route
`/ui/app-chain/authenticated-map/?chain={chainId}` independently rechecks
identity before rendering any record: it requires the domain metadata response
to carry `apiVersion = authenticated-map-domain-v1`, the selected `chainId`,
`stateMachineId = authenticated-map`, and `verificationLevel =
authenticated-record`, and every subsequent exact-record response is
re-asserted against the same identity. A chain running another state machine
receives a bounded unsupported view with no authenticated-map parsing; a
failed identity probe receives a bounded diagnostic view. Pending pages are
accepted only with `verificationLevel = DERIVED_FROM_PENDING_INDEX`, a source
index proof key, and no exact-record fields, and the console labels them as
derived projections of the committed pending index rather than proof-key
values. Composed role-workflow responses are accepted only without the map
API's version fields, matching the server envelope split.

## Console views delivered

Views 1-4 and 9 render for every profile: overview (chain/genesis/profile
identity, finalized height and root, backend and commitment identity from the
state-identity route, collection count, validation catalog, governed
capability), collections, exact entry lookup (presence, revision, status,
controller, logical hash, bounded canonical CBOR/hex value preview, exact
proof key, one-click proof retrieval and host verification), receipts by
message id, mutation construction, and generic proof
retrieval/verification with block and finality-certificate context. Views 5-8
(actors and organizations with key epochs, direct/approval policies and
administrator authority with revision selectors and current-pointer facts,
pending approvals with proposal decisions and deadline distance, governance
changes with component command results, and direct/approval consumption
lookups) appear only when the committed genesis reports governed
authorization. The optional derived entry explorer view states the point-query
model and the mandatory projection identity/version/lag/rebuild labelling, and
reports that no first-party entry projection bundle is configured; shipping
such a projection remains optional future work, not a Phase-F deliverable.

The mutation builder encodes the canonical command in the browser with a
reviewed minimal CBOR encoder proven byte-identical to
`AuthenticatedMapContract.encodeCommand` by cross-language golden vectors, and
preflights locally against the committed collection bounds and the contract's
per-operation precondition rules. Open/owner/member commands submit directly;
`governed-role` and `approval` collections switch the builder to the §10.3
export/import workflow — the console prints the offline CLI invocation for the
canonical action and accepts the externally signed envelope, and it never asks
for or retains seed phrases or private keys. Submission tracking distinguishes
the four §10.3 levels as separate observed facts: HTTP acceptance, block
finalization, state-machine receipt or component command result, and the
re-fetched entry state.

## Showcase extension

The light-profile authenticated-map chain now demonstrates all three Phase-F
authorization families. The generator emits a governed genesis with three
organizations, four deterministic demo actors, an administrator authority, the
`issuer-write` direct-role policy, and the `product-release` approval policy
requiring two auditor approvals distinct by organization, alongside two new
collections: `governed-catalog` (governed-role) and `released-products`
(approval). `./showcase.sh run authenticated-map` exercises the basic
collections as before, then completes a direct-role write through
`action`/`direct-preimage`/`direct-complete`/`command` CLI authoring with the
signature produced by the demo-only stdlib-Python signer
(`tools/showcase_signer.py`, cross-checked against the independent Ed25519
verifier and the Java key derivation), and completes an approval flow through
signed PROPOSE/APPROVE statements from actors in two distinct organizations,
terminal-`APPROVED` verification, approval-reference evidence, and exactly-one
consumption, verifying receipts, consumption records, and proposal state
through the bounded domain API. The driver prints the packaged console route
for inspecting every governed record.

## Review corrections

An adversarial verification pass against the server and CLI sources caught
four issues before qualification. First, the pre-existing showcase codec still
submitted the retired legacy command encoding for basic collections, which the
Phase-B composite deliberately rejects; every basic submission path in
`showcase.sh` now wraps the codec output into the final v1 envelope through
the release-matched CLI (`action` with a basic assignment, `command` with no
evidence), pinned by a contract-level wrap test. Second, the console's
governed CLI hint mislabelled the assignment's fourth field, which is the
one-based evidence handle rather than a policy revision. Third, finality
tracking re-read the mutation form instead of capturing the submitted
collection/key, and imported-command tracking could never reach its terminal
state. All are fixed and covered by the gates below. A known timing edge
remains recorded for Phase G: the direct-authorization demo window is 90
blocks, so a cluster stalled for most of the 120-second finalization allowance
could see a deterministic deadline rejection.

## Qualification evidence

Focused tests cover the origin/credential regression suite, the TS canonical
command encoder against cross-language golden vectors, envelope identity
gates, capability discovery, the packaged static-page and security-header
contracts, the governed showcase genesis (including the shell/Java demo-seed
and key-derivation agreement vectors), and the packaged distribution
generator:

```bash
./gradlew :appchain-stdlib-contracts:check :appchain-stdlib:check \
  :appchain-role-workflow-contracts:check :appchain-role-workflow:check \
  :appchain-client:check :appchain-devtools:check :appchain-showcase:check \
  :appchain-showcase:showcaseDistributionContract :console-ui:check :app:test
```

The run completed successfully with 201 Gradle tasks. The console gate
additionally enforces the 1 MiB embedded-asset budget, svelte-check, and the
static console contract including the new route and its `data-console-route`
marker.

A live three-node light-profile cluster run of the packaged distribution
completed the full scenario on 2026-08-04: all four basic collections
finalized under the final v1 envelope, both schema/plugin negative cases were
filtered before finalization, the direct-role write applied with externally
signed evidence and a retained `(actorId, authorizationId)` consumption
record, and the `product-release` proposal reached terminal `APPROVED` with
one `independent-auditors` decision from each of the two auditor
organizations before executing exactly once. Proposal, consumption, and actor
records were re-read from a non-submitting node with identical envelopes, and
the packaged console route served with the §10.5 security headers.
Browser-automation coverage of the new route remains Phase G qualification
work.

Phase G owns the full qualification matrix and the final v1 freeze.
