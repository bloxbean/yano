# ADR-025.2 Phase D — Approval-gated execution

## Status

Implemented and qualified on 2026-08-04.

## Approval lifecycle delivered

Governed authenticated-map profiles now accept the reusable ADR-019
actor-signed `PROPOSE`, `APPROVE`, `REJECT`, and `CANCEL` envelopes on the
role-approval workflow. Proposal creation requires a current active approval
policy and eligible proposer actor. Decisions verify the current actor,
organization, key epoch, role, clause, signature, and configured actor- or
organization-distinctness rule.

Each proposal freezes the policy revision and digest. Later policy suspension
or replacement does not reinterpret accepted decisions. Terminal proposal
records retain the accepted decision signatures and actor, organization, key,
role, clause, and height facts. Partial accepted decisions are retained when a
proposal expires.

The generic ADR-019 actor statement remains reusable. Its authenticated-map
payload hash is scoped without changing that statement shape:

```text
Blake2b-256(
  "yano:authenticated-map:approval-payload:v1\0" ||
  authenticatedMapGenesisId || actionCommitment
)
```

The map reference carries the plain complete-action commitment. Execution
recomputes the scoped payload hash and rejects wrong genesis, action, policy,
revision, coverage, deadline, or terminal outcome. Java and the independent
Python verifier reproduce the new vector.

## Atomic execution and replay

An approved reference is usable only while its frozen proposal is `APPROVED`
and within its deadline. Successful execution stages every map entry, receipt,
and one immutable consumption record under the proposal ID in the same map
component transition. There is no collection or action-scope suffix that can
permit a second execution.

All authorization references are checked before transition writes. A failed
precondition, mixed batch, duplicate reference, payload substitution, or replay
writes no entry and consumes no proposal. Multiple approved references in one
batch are therefore all consumed or none are.

## Bounded liveness and operational results

Approval and actor-governance processors maintain canonical bounded pending
indexes plus deadline, proposer, policy, and authority markers. At the start of
every block workflow, including an empty block, expired work is materialized
and its capacity, markers, and aggregate statistics are reclaimed without a
per-ID poke message. Authority revision changes likewise remove bounded
superseded governance work.

Every decodable finalized approval or actor-governance command retains a
canonical result keyed by its exact 32-byte message ID. Saturation returns the
stable `CAPACITY_EXCEEDED` code rather than an indistinguishable no-op. Bounded
pending-approval and pending-governance page queries use exclusive canonical
cursors and enforce both the global contract limit and the smaller
genesis-selected page limit.

The review found that the normal command CBOR decoder ceiling was too small for
the frozen 1,024-governance and 4,096-approval index maxima. Internal pending
indexes now use a separately frozen 1,048,576-byte and 20,483-item decoder
bound. Tests round-trip indexes beyond the command-envelope byte/item limits.
Restart verification checks pending records, markers, per-dimension bounds,
and approval aggregate counts before accepting retained governed state.

## Query and proof surface

Governed profiles expose exact or bounded component queries for:

- approval proposals and aggregate statistics;
- approval and governance pending pages;
- registry-governance, policy-governance, and approval command results; and
- authenticated-map approval consumption by proposal ID.

The retained records and frozen `q/`, `g/`, `l/`, `x/`, `i/`, `r/c/`, and
approval-consumption keys are addressable through the generic composite proof
surface. Phase E owns the domain HTTP projections and assembled, root-checked
multi-record proof bundles.

## Qualification evidence

Focused tests cover frozen-policy execution, threshold satisfaction,
rejection, proposer and governance cancellation, distinctness, invalid
signatures, partial-decision expiry, canonical cursor pagination, restart
corruption detection, stable capacity results, empty-block reclamation,
same-block approval before map execution, wrong-genesis payload substitution,
one-time replay, and all-or-none multi-reference batches.
