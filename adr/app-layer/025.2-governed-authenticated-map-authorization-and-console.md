# ADR-025.2: Governed Authorization and Capability-Gated Console for Authenticated Map

## Status

Accepted for implementation as a pre-release amendment to the
`authenticated-map` v1 contract. Phase A contracts and work bounds are
implemented and independently verified. Phase B composite assembly and Phase C
governed-role authorization and Phase D approval-gated execution are
implemented and qualified. Phase E configuration, client, domain-API, and
proof-bundle work is implemented and qualified. Phase F console and showcase
work is implemented and qualified; Phase G final qualification and the v1
freeze are not yet complete.

`authenticated-map` has not been merged, publicly released, or used to create
a supported chain genesis. Therefore this decision deliberately reopens v1
rather than preserving the repository's intermediate three-policy contract and
introducing a premature v2. The final v1 contract includes all authorization
modes defined here. Its canonical genesis, commands, state keys, golden vectors,
proof fixtures, clients, documentation, and qualification results must be
regenerated before merge.

After the first supported release or published chain genesis, an existing v1
genesis must never be reinterpreted. A later incompatible change requires a new
contract version and an explicit migration or governed profile-evolution plan.

2026-08-04

## 0. In plain words

An app-chain member key answers a consensus and relay question. A domain actor
key answers a business authorization question. They are deliberately different
identities.

The intermediate authenticated-map implementation understands only:

- `open`: any admitted signed sender;
- `owner`: the first writer/controller; and
- `member`: any active app-chain member.

Those modes are useful, but they cannot express "an active issuer may update
this collection" or "two auditors from distinct organizations and one
regulator must approve this exact batch." ADR-019 already supplies reusable
domain actors and role-aware approvals. Making applications operate a separate
role chain and then copy an approved result into an authenticated-map chain
would leave the important link off chain and non-atomic.

This ADR makes the final authenticated-map v1 authorization catalog:

1. `open`;
2. `owner`;
3. `member`;
4. `governed-role`; and
5. `approval`.

Operators and applications still select one user-facing state machine:

```text
state-machine: authenticated-map
```

Internally, Yano assembles one committed composite product:

```text
authenticated-map v1
  |
  +-- domain-actor registry
  +-- role-aware policies and approvals
  +-- authenticated-map collections and entries
  +-- declared authorization/execution workflow
```

This is one app chain, one ordered block history, one atomic transition, one
state root, and one finality certificate. The components are not separate
operator-managed state machines.

A governed profile also starts with a closed, genesis-authenticated business
governance root: administrator organizations, administrator actors and keys,
proofs of possession, the initial administrator-authority revision, and any
initial collection policies selected by the project. Current app-chain members
transport those actor-signed governance decisions, but member-key rotation does
not silently add, remove, or strand business administrators.

The same product receives a dedicated route in the unified Yano console. The
route appears only for a selected chain whose authenticated state-machine
identity is `authenticated-map`. It shows collection configuration, exact
entry queries and proofs, actors, policy revisions, pending approvals,
governance changes, receipts, and approval-consumption state. Basic
authenticated-map profiles hide governed-only panels.

## 1. Problem

### 1.1 Consensus members are not business actors

`AppMessage.sender` identifies the member node that authenticated or relayed a
message. It does not prove which employee, auditor, regulator, issuer, device,
or application service authorized the business operation. Treating member
keys, REST API keys, or UI sessions as business roles would conflate distinct
trust and rotation lifecycles.

### 1.2 The parent ADR names governed policies but Phase 0 deferred them

ADR-025 section 3.6 lists `governed-role` and approval-reference authorization
as candidates. The implemented Phase 0 baseline deliberately froze only
`open`, `owner`, and `member` until explicit component state and workflow
contracts existed.

ADR-019 has since implemented the missing actor registry, policy, signature,
governance, and approval building blocks. Because authenticated-map is still
pre-release, retaining the temporary three-policy subset would create a v2
immediately after v1 for a requirement already present in the parent ADR.

### 1.3 Two independent state machines would not enforce the binding

A role-approval chain can prove that actors approved `(payloadDomain,
payloadHash)`. A separate authenticated-map chain cannot, by itself, prove that
the bytes subsequently written were those approved bytes, that the approval
was still executable, or that it was consumed once.

An external orchestrator could query an approval and then submit a map command,
but that would be an application convention rather than a deterministic
authorization rule. A crash or substitution between the two steps could leave
the approval and mutation inconsistent.

### 1.4 Direct sibling-state reads would break the component boundary

Adding actor-registry keys directly to `AuthenticatedMapStateMachine` and
letting it construct sibling physical keys would couple unrelated state
layouts, undermine ADR-013.2 isolation, and make future component evolution
unsafe.

The ADR-025.1 value-validator SPI is also deliberately unsuitable. A validator
sees only `(collectionId, applicationKey, value)` and cannot read actors,
membership, policy, time, network, filesystem, or another key. Turning it into
an authorization oracle would destroy its deterministic trust boundary.

### 1.5 Authorizers and policies must evolve after genesis

A collection's trust model must be stable, but organizations, employees,
devices, keys, roles, and approval thresholds change. Requiring a new chain
generation whenever one actor rotates a key is operationally unacceptable.
Allowing a node-local YAML edit to change an authorization rule is a consensus
fork.

The contract therefore needs stable genesis bindings to versioned,
authenticated policy state whose revisions advance through threshold
governance.

### 1.6 Generic hexadecimal operations are not enough

Authenticated-map is intended to support many registry-shaped applications.
Operators need to see which collection and policy rejected a command, which
approvals are still missing, whether an actor or key revision was current, and
which entry/approval facts are proved by a finalized root.

The generic app-chain console correctly treats arbitrary message bodies as
opaque. Adding authenticated-map parsing to that page would couple the generic
view to one product. Loading JavaScript supplied by arbitrary validator plugins
would weaken CSP and supply-chain guarantees. A reviewed, capability-gated,
console-owned view is required.

### 1.7 The pre-release window is the correct time to change v1

The current branch has executable vectors and tests, but they are development
artifacts rather than a published compatibility promise. Reopening the
contract now has a bounded cost. Deferring the decision would require versioned
migration, dual codecs, and long-term compatibility code immediately after the
first release.

### 1.8 Business administration must survive membership-key rotation

ADR-019's current implementation derives registry administrators from the
membership epoch at height 1 while the outer app-message transport accepts only
current member keys. After a member-key rotation, the old key remains named as
an administrator but can no longer submit, while the replacement member key is
not a business administrator. If enough such keys rotate, actor and policy
governance freezes.

Routing administrator-authority changes only through ADR-015 profile
governance is not a sufficient emergency path. A `STAGING` profile proposal
cannot currently be threshold-cancelled, and profile-epoch exhaustion is
detected at activation rather than proposal admission. This ADR therefore does
not make raw member keys the default authenticated-map business-administrator
identity. It defines stable administrator actors whose signed decisions may be
relayed by any current member, and makes the profile-governance liveness fixes
explicit prerequisites.

### 1.9 A bound without deterministic reclamation is not a liveness contract

The existing role workflow caps pending approvals and governed mutations, but
materializes expiry only when a later command names the same ID. A malicious or
abandoned workload can fill the cap and require one recovery message per stale
record. For an approval-gated collection, that prevents new governed writes.

Authenticated-map v1 therefore needs bounded deadline buckets, automatic
expiry at block height, atomic pending-index updates, and explicit capacity
results. Silent no-ops and operator-driven per-ID expiry are not sufficient for
this product.

## 2. Goals and non-goals

### 2.1 Goals

- Keep `authenticated-map` as one user-facing state machine and app chain.
- Include all five authorization modes in the final v1 contract.
- Reuse ADR-019 actor, policy, approval, and crypto contracts while adding a
  profile-owned actor-administrator governance adapter.
- Decouple business-administrator identity and key rotation from app-chain
  membership while retaining member-authenticated transport.
- Permit a governed profile to start from a canonically validated closure of
  genesis organizations, actors, keys, administrator authority, and policies.
- Bind actor signatures and approvals to the exact canonical map action.
- Apply a map mutation and consume its authorization atomically under one root.
- Support governed actor, key, role, direct-role policy, and approval-policy
  revisions after genesis.
- Keep collection authorization kind and stable policy binding consensus-bound.
- Preserve the state-free ADR-025.1 validator contract.
- Make mixed-collection batches deterministic, bounded, and all-or-nothing.
- Reclaim expired approval/governance capacity automatically and expose a
  deterministic result for every decodable finalized command.
- Bound worst-case actor-signature verification work per candidate block.
- Expose proof-oriented, root-fixed domain queries for map and authorization
  facts.
- Provide a capability-gated authenticated-map console without executing
  plugin-supplied UI code.
- Preserve exact replay, restart, snapshot, catch-up, and cross-member root
  agreement for every supported commitment backend.

### 2.2 Non-goals

- Replacing app-chain membership, sequencing, finality voting, or L1 anchors.
- Treating REST/API credentials, TLS identities, or UI sessions as domain-actor
  signatures.
- Building a general policy language, BPMN engine, or arbitrary boolean
  authorization expression system.
- Combining `owner` with a role or approval policy in v1. A collection chooses
  exactly one authorization kind.
- Making a role approval prove that an external business claim is true.
- Automatically executing arbitrary payload bytes when an approval reaches its
  threshold.
- Retrospectively invalidating a terminal approval when an actor later rotates
  a key or loses a role.
- Letting value-validator plugins read actor, role, policy, or map state.
- Adding range queries, joins, secondary indexes, or authoritative full-map
  enumeration to authenticated-map consensus state.
- Loading arbitrary plugin HTML, JavaScript, CSS, templates, or remote assets
  into the Yano console.
- Storing member, administrator, or actor private keys in Yano configuration,
  app state, Studio, the console, or generated projects.
- Recovering in band after enough independent administrator actors lose all
  usable keys to make the configured threshold impossible. That is an explicit
  break-glass profile/new-genesis event, not an implicit membership privilege.

## 3. Decision summary

1. The final unreleased `authenticated-map` v1 contract supports `open`,
   `owner`, `member`, `governed-role`, and `approval`.
2. The public provider and state-machine selector remain
   `authenticated-map`; no `authenticated-approval-map` selector is introduced.
3. The provider returns a committed ADR-013.2 composite assembly containing the
   reusable domain-actor and role-approval components, an authenticated-map
   component, and declared workflows.
4. The authenticated-map workflow owns `authenticated-map.command.v1`; map
   state is not directly writable through an unaudited component route.
5. Each collection commits exactly one authorization kind. A governed kind
   additionally commits a stable policy ID.
6. Direct-role and approval-policy contents are immutable revision records with
   governed current-revision pointers. Routine policy changes do not rewrite
   collection genesis.
7. `governed-role` requires one actor-signed authorization satisfying the
   collection's current direct-role policy at the execution height.
8. `approval` requires a terminal ADR-019 proposal whose policy, revision,
   payload domain, payload hash, deadline, and mutation coverage match the
   submitted action.
9. Every governed authorization binds the complete canonical map action,
   including all mutations, values, preconditions, ordering, collection IDs,
   and authorization assignments.
10. Direct authorizations and approval references are consumed exactly once on
    a successful action. Consumption and map writes share one atomic state
    transition.
11. A rejected action consumes no authorization and changes no entry.
12. Outer member identity remains the authorization subject for `owner` and
    `member`; embedded domain-actor identity is the subject for
    `governed-role` and actor approval decisions.
13. Governed profiles commit a stable administrator-authority ID. Its immutable
    current revision names distinct administrator actor IDs and a threshold.
    Administrator actors sign exact governance statements; any current member
    may relay them without becoming a business administrator.
14. A governed genesis contains a canonically validated minimum administrator
    closure and may contain initial organizations, actors, direct-role policies,
    and approval policies. Genesis authenticates those revision-1 records; it
    does not require a post-start ceremony to establish the governance root.
15. Actor/organization/key/role, policy, and administrator-authority revisions
    use bounded `PROPOSE -> APPROVE_TO_THRESHOLD -> ACTIVATE` state transitions.
    An authority revision is approved by the prior current authority.
16. Routine actor, policy, and administrator-authority changes use ordinary
    state-machine topics. Collection kind, stable policy/authority namespace,
    executable component, authorization algorithm, and consensus-limit changes
    require a new genesis or a cataloged ADR-015 profile transition.
17. Authorization evaluation follows a frozen block-stage order: profile
    activation, domain-actor components, role/policy workflows, then the
    authenticated-map workflow. Terminal approvals preserve the facts accepted
    at their decision heights.
18. Pending approvals and governed mutations use bounded deadline buckets that
    are deterministically expired before new commands at each height. Capacity
    rejection is authenticated and distinguishable from transport acceptance.
19. The state machine adds bounded pending-approval and pending-governance query
    indexes; it does not add authoritative entry enumeration.
20. The unified console adds a built-in authenticated-map route gated by
    state-machine identity and domain-API version. Governed panels are gated by
    authenticated genesis capability.
21. Arbitrary validator plugins may supply validation code to the trusted node
    process under ADR-025.1, but never executable console code.
22. Canonical/bound checks precede stateless signature verification; stateful
    actor eligibility remains authoritative in apply. Frozen evidence and block
    work bounds cap even correctly signed but ineligible traffic.

## 4. Product identity and internal assembly

### 4.1 One external state machine

The operator-facing selector remains:

```yaml
state-machine: authenticated-map
```

The state-machine provider creates a `CompositeStateMachine` using machine ID
`authenticated-map`, following the existing `role-approvals` and
`role-evidence` precedent. The committed component order is:

```text
1. domain-actors
2. role-approvals
3. authenticated-map
```

The committed workflow catalog contains:

```text
role-approval-v1
authenticated-map-authorization-v1
```

The exact component generations, state schemas, topics, workflow participants,
quotas, and aggregate-query limits contribute to the composite profile digest
and authenticated-map genesis identity.

This internal composition does not create multiple consensus instances. A
block is executed once through the declared workflow order and produces one
backend-selected state root.

### 4.2 Route exposure is genesis-bound

Every profile exposes `authenticated-map.command.v1`. The actor and
role-policy/approval routes are exposed only when at least one collection uses
`governed-role` or `approval`.

When governed authorization is absent:

- `open`, `owner`, and `member` behave normally;
- actor/policy/approval commands are rejected as unsupported rather than
  accepted as silent no-ops; and
- governed-only console panels remain hidden.

When governed authorization is present, the component and route identities are
part of genesis. Copying a plugin or editing local configuration cannot enable,
disable, reorder, or replace them.

### 4.3 Component isolation

The authenticated-map component owns collection metadata, entries, receipts,
authorization-consumption records, and map-specific query indexes. The
domain-actor component owns organizations, actors, key epochs,
administrator-authority revisions/current pointer, actor/authority governance
records, and their pending/deadline indexes. Keeping authority with the actor
registry lets registry governance validate its own actor/key/authority state
without a sibling-state read. The role-approval component owns policy
revisions, proposals, accepted decisions, statistics, and its pending/deadline
indexes.

No component constructs another component's physical key or reads the root
store directly. The authorization workflow receives declared state views for
the exact participant generations. Profile validation rejects missing,
ambiguous, reordered, or undeclared participants.

Physical proof keys remain composite-namespaced. Domain APIs and clients return
the exact physical key instead of requiring callers to reproduce namespace
encoding.

## 5. Collection authorization contract

### 5.1 Closed v1 catalog

| Kind | Authorization subject | Rule |
|---|---|---|
| `open` | Outer authenticated sender | Any admitted signed sender may mutate |
| `owner` | Outer authenticated sender | First writer becomes controller; only it may mutate |
| `member` | Outer authenticated sender | Sender must be active app-chain member at candidate height |
| `governed-role` | Embedded domain actor | Active actor/key satisfies the current direct policy |
| `approval` | Referenced role proposal | Exact action has a valid terminal, unconsumed approval |

Unknown authorization integers or text values are rejected while rendering,
decoding genesis, initializing the machine, and decoding proof metadata.

Only `owner` entries carry a controller and support
`TRANSFER_CONTROLLER`. Governed collections do not reinterpret an actor ID or
member relay key as an owner controller. Compound rules such as
`owner AND approval` require a future explicitly versioned policy language or
a custom composite. Applications that need ordinary owner-controlled records
plus separately approved exceptional actions model them as separate
collections/keyspaces, for example owner-controlled product records and an
approval-controlled recall or release collection. The approval collection
refers to the product key in its canonical value; it does not weaken ownership
of the product collection.

Genesis initial entries are authenticated by genesis rather than a runtime
authorization. An owner initial entry must name its controller; other kinds
must not carry one.

### 5.2 Stable policy binding

The final v1 collection descriptor adds a bounded
`authorizationPolicyId`:

```text
CollectionDescriptorV1
  id
  authorizationKind
  authorizationPolicyId
  restoreAllowed
  maxKeyBytes
  maxValueBytes
  valueEncoding
  validatorId
```

For `open`, `owner`, and `member`, `authorizationPolicyId` must be empty. For
`governed-role` and `approval`, it must be a non-empty canonical policy ID.

The binding is genesis-stable. Policy *contents* evolve through immutable
revisions and a governed current pointer. A missing, suspended, revoked,
wrong-kind, or corrupt policy fails closed.

### 5.3 Direct-role policy

`governed-role` resolves a `DirectRolePolicyV1`:

```text
DirectRolePolicyV1
  policyId
  revision
  status: ACTIVE | SUSPENDED | REVOKED
  requiredRole
  maximumAuthorizationLifetimeBlocks
```

Policy IDs and roles use the bounded canonical ADR-019 identifier rules. A
revision is immutable, and activation advances the current pointer by exactly
one. Activation rejects a policy ID already used by a different policy kind.

V1 deliberately has one required role per direct policy. Changing that role or
temporarily suspending the policy is a governed policy revision. More complex
thresholds use `approval` rather than extending direct-role semantics.

### 5.4 Approval policy

`approval` resolves the existing ADR-019 `ApprovalPolicyV1` family:

- optional proposer roles;
- one or more conjunctive required clauses;
- role and minimum count per clause;
- distinctness by actor or organization;
- rejection mode; and
- maximum proposal lifetime.

A proposal freezes the exact policy ID, revision, and digest that were current
when accepted. Callers cannot submit a weaker per-action threshold.

### 5.5 Actor eligibility

An actor authorization or decision is eligible only when, at its deterministic
acceptance height:

- the referenced actor revision is the registry's current revision;
- the actor is `ACTIVE`;
- the referenced organization revision is current and `ACTIVE`;
- the actor record contains the policy-required role;
- the referenced key exists, is active for that height, and uses the supported
  algorithm; and
- the signature verifies over the exact domain-separated statement.

REST authentication determines who may call a node. It is not any of these
checks. Any member may relay a correctly actor-signed envelope; relaying does
not make that member the business actor.

## 6. Canonical action and authorization evidence

### 6.1 Separate action core from evidence

The final v1 command has two canonical layers:

```text
MapActionV1
  ordered mutations
  authorization assignments

AuthenticatedMapCommandV1
  action
  bounded authorization evidence
```

`MapActionV1` includes every collection ID, application key, operation, value,
expected revision, expected logical-value hash, new controller, submitted
order, policy ID, authorization kind, evidence handle, and covered mutation
index. It contains no signature bytes.

Its action commitment is:

```text
Blake2b-256(
  "yano:authenticated-map:action:v1\0" ||
  canonical MapActionV1 bytes
)
```

Direct actor statements bind chain ID and authenticated-map genesis ID. Reused
ADR-019 approval statements bind chain ID and use the fixed payload domain
`yano.authenticated-map.action.v1`. Their payload hash is the genesis-scoped
commitment:

```text
Blake2b-256(
  "yano:authenticated-map:approval-payload:v1\0" ||
  authenticatedMapGenesisId || actionCommitment
)
```

The final map reference still carries the plain action commitment, allowing
the workflow to recompute and verify the scoped proposal hash. An action or
authorization prepared for one chain generation therefore cannot be replayed
on another without changing the reusable ADR-019 statement shape.

The exact CBOR arrays, integer discriminants, identifier bounds, evidence
bounds, digest vectors, and signature preimages must be frozen in the contract
phase before implementation proceeds.

### 6.2 Basic authorization assignments

Mutations for `open`, `owner`, and `member` carry no embedded authorization
evidence. They are checked against the outer message sender and candidate
membership/entry state exactly as defined by ADR-025.

### 6.3 Direct actor authorization

One `MapActorAuthorizationV1` contains at least:

```text
authorizationId
chainId
genesisId
actionCommitment
coveredMutationIndexes
policyId + policyRevision
actorId + actorRevision
keyId
publicKey
issuedHeight
deadlineHeight
signatureAlgorithm
signature
```

The actor signs a fixed domain-separated statement containing every field
except the signature. `authorizationId` is a caller-chosen canonical 32-byte
identifier and is also part of the signed statement; it is not inferred from
the outer message ID. `publicKey` is the canonical 32-byte key claimed by the
statement. Stateless admission may verify the signature against that key, but
authoritative apply must additionally require exact equality with the named
current actor key and repeat verification.

The workflow requires the referenced direct-role policy to be current and
active at execution, verifies actor eligibility and the signature, requires
`issuedHeight <= executionHeight < deadlineHeight`, enforces the policy's
maximum authorization lifetime, and checks that every covered collection binds
that policy ID.

One actor authorization may cover several mutations sharing the same direct
policy. Mutations requiring different policies need separate evidence.

### 6.4 Approval reference

One `MapApprovalReferenceV1` contains at least:

```text
proposalId
actionCommitment
coveredMutationIndexes
policyId + policyRevision
```

The workflow loads the proposal through its declared role-approval view and
requires:

- terminal status `APPROVED`;
- matching payload domain and genesis-scoped action payload hash;
- matching policy ID and revision;
- a valid deadline at execution height;
- coverage of collections bound to that policy; and
- no prior authenticated-map consumption claim for the proposal.

Reaching approval threshold does not synthesize a map message. The proposal
stores a hash, not arbitrary map bytes. An application submits the final
authenticated-map command containing the original bytes and proposal
reference; any member may relay it. Relay identity is deliberately not an
executor or owner identity for an `approval` collection.

The first valid relay may choose the first eligible inclusion height and
therefore the successful receipt/message identity. It cannot change the action,
controller, policy, or mutation result, and a failed relay does not consume the
proposal. V1 does not infer an intended executor or a not-before constraint from
the transport sender. An application that needs either rule requires an
explicitly versioned policy/action field rather than relying on relay identity.

### 6.5 Mixed batches

A v1 batch may mix authorization kinds and collections. Its evidence table is
bounded and canonical.

- Every governed mutation index is covered exactly once by matching evidence.
- Basic mutations are not covered by actor or approval evidence.
- One evidence item may cover several indexes bound to the same policy.
- Multiple approval policies require multiple proposal references.
- Evidence entries and coverage lists are uniquely ordered and reject
  duplicates, overlap, gaps, out-of-range indexes, and unused evidence.
- Every actor and approval signs or approves the complete action commitment,
  not a detachable mutation fragment. An approver therefore sees every change
  in the atomic batch even when its policy covers only a declared subset.

If any authorization, precondition, lifecycle rule, encoding, schema, plugin,
or resource bound fails, no mutation or consumption record is written.

### 6.6 One-time consumption and replay

Successful direct authorization writes a consumption record under the
domain-separated tuple `(actorId, authorizationId)`. The same actor cannot
reuse an ID, including across actor revisions, keys, policies, or actions; a
different actor using the same 32-byte ID occupies a different key and cannot
deny the first actor's authorization.

Successful approval execution writes exactly one authenticated-map consumption
record under the domain-separated `proposalId`. There is no collection,
coverage, mutation, or undefined "action scope" suffix that would permit one
proposal to be consumed more than once. The proposal already binds the complete
action commitment and its ID is unique in the role-approval component.

A record binds the action commitment, applied height, receipt/message identity,
and affected mutation indexes. A direct record also snapshots the accepted
policy, actor, organization, role, key, statement digest, and signature
identities needed to explain the verdict. An approval record points to the
retained proposal and its frozen decision facts rather than duplicating the
complete decision trail.

Consumption records are included, retained, queryable, and provable. Reusing an
ID or proposal for a different or repeated action is rejected. Consumption is
staged with every map entry and receipt in the same candidate update and
durable commit.

A rejected action does not consume evidence. Actor and approval deadlines,
exact action binding, mutation preconditions, and one-time claims prevent a
rejected authorization from becoming a general future capability.

## 7. Deterministic transition and atomicity

### 7.1 Evaluation order

For a structurally valid command, authoritative application evaluates:

1. canonical action/evidence structure and configured bounds;
2. collection existence and authorization-assignment consistency;
3. duplicate action, authorization, and approval-consumption claims;
4. outer sender, actor, policy, proposal, deadline, and signature rules;
5. entry lifecycle and compare-and-set preconditions;
6. ADR-025.1 canonical encoding and optional value validation;
7. the complete staged next entries, consumption records, indexes, and receipt;
8. one atomic component/composite write.

Authorization and operation preconditions run before value validation so a
validator cannot become an oracle for an unauthorized caller. Validator
plugins still receive only `(collectionId, applicationKey, value)`.

### 7.2 Candidate-height state

Membership, actor current pointers, organization status, key validity, direct
policy current pointers, proposals, and consumption claims are evaluated at
the candidate block's deterministic state point. The final v1 stage order is:

1. activate any previously scheduled composite profile for this height, then
   process profile-governance commands that can schedule only a later height;
2. expire due actor-registry governance records and apply all routed
   domain-actor component commands in block message order;
3. expire due policy-governance/approval records and apply all routed
   role-policy and approval workflow commands in block message order; and
4. apply authenticated-map commands in block message order with
   read-your-writes across successful map actions.

Components run before workflows, and workflows run in committed profile order.
Consequently an actor/key revocation accepted anywhere in a block is visible to
every approval decision and map authorization in that block. A role proposal
that reaches approval in stage 3 may be consumed by stage 4 in the same block,
even if its map message appeared earlier in the block's global message list.
This stage ordering, not cross-topic arrival order, is the consensus contract.

Candidate admission sees committed pre-block state and cannot authoritatively
reject a governed command merely because an actor, policy, or proposal is not
yet eligible there; an earlier stage in the same candidate may make it eligible
or revoke it. Admission performs canonical/bound checks and any self-contained
stateless signature check. Stateful eligibility and same-block ordering are
authoritative only in apply. This does not weaken ADR-025.1: its
pre-validation/application equivalence remains scoped solely to the pure value
validator verdict.

No node-local cache, wall clock, filesystem, network service, environment
variable, REST session, or external identity provider participates in the
verdict.

### 7.3 Receipts and stable rejection codes

Every decodable finalized authenticated-map command retains an authenticated
receipt. Decodable actor-registry, administrator-governance, policy-governance,
and approval commands likewise retain a component-owned command result so an
HTTP sequencing acceptance cannot be mistaken for a state transition. In
addition to existing lifecycle and validation errors, v1 freezes bounded codes
for at least:

- missing, duplicate, overlapping, or unexpected evidence;
- unknown, missing, suspended, revoked, stale, or wrong-kind policy;
- actor, organization, revision, role, key, or signature rejection;
- expired actor authorization or approval;
- proposal absent, non-terminal, rejected, cancelled, expired, or hash-mismatched;
- authorization or proposal already consumed;
- stale administrator authority or governance mutation superseded by an
  authority handover;
- pending capacity exhausted or selected deadline bucket full; and
- governance capability disabled by genesis.

Receipts expose safe identifiers and commitments, not private key material or
unbounded parser/plugin errors. Candidate-admission rejection and finalized
state-machine rejection remain distinguishable.

### 7.4 Deadline buckets and capacity reclamation

Pending approval proposals and governed actor/policy mutations are indexed by
canonical `(deadlineHeight, id)` keys. Phase A freezes a maximum pending count
plus per-proposer-actor, per-policy/authority namespace, and per-deadline-height
sub-limits. Creation that would exceed any bound produces an authenticated
capacity result and writes no proposal/mutation. One eligible actor therefore
cannot occupy the entire shared budget unless the explicitly frozen profile
sets its per-actor bound equal to the global bound.

Governed mutations are additionally indexed by their frozen administrator-
authority revision so an authority handover can supersede the complete bounded
old pending set without scanning historical state.

At the beginning of the owning stage at height `H`, the workflow transitions
every still-pending record with `deadlineHeight < H` to `EXPIRED` before
evaluating new commands. Because each deadline bucket is independently bounded,
processing the complete due bucket has a deterministic worst-case cost. Every
terminal transition removes its pending-index row and updates counts in the
same component write. Empty blocks still run the expiry stage.

No poke message naming each stale ID is required. Pending counts, pending pages,
individual effective status, and capacity availability agree at one committed
height/root after restart, replay, catch-up, and rollback.

## 8. Governance and policy evolution

### 8.1 Actor-authenticated governed mutation protocol

Organizations, actors, actor keys/roles/status, direct-role policies, approval
policies, administrator authority, and emergency pending-proposal cancellation
reuse the existing bounded governed-mutation lifecycle:

```text
PROPOSE -> APPROVE_TO_THRESHOLD -> ACTIVATE
```

Authenticated-map changes the authorization strategy, not the lifecycle. A
governed profile commits a stable authority ID whose current immutable revision
is conceptually:

```text
AdministratorAuthorityV1
  authorityId
  revision
  sorted administratorActorIds
  distinctActorThreshold
  maximumMutationLifetimeBlocks
```

An administrator vote is an actor-signed, domain-separated statement binding
at least chain ID, authenticated-map genesis ID, authority ID and revision,
mutation ID and hash, the proposed not-before activation height and expiry,
decision, actor/revision/key/public key, issued height, and deadline. The actor,
organization, and key must be current and active when the vote is accepted.
Duplicate actor votes are no-ops; relaying the same vote through several
members never multiplies it. The accepted vote snapshots the eligibility facts
used at that height.

The proposing actor's signed statement counts as the first approval. Once the
frozen threshold is present, any current member may relay the exact activation
command; relay identity contributes no business vote. The proposal's signed
activation constraint permits activation only at or after its not-before
height and no later than its expiry. The proposer may actor-sign cancellation,
and a threshold of current administrator actors may cancel or supersede
abandoned/compromised work.

Registry and administrator-authority mutations use the `actors.command.v1`
contract family. Direct-role and approval-policy mutations use
`role-approvals.command.v1` or contract-phase-compatible typed routes owned by
the same declared workflows. The standard member-signed app-message endpoint
transports their canonical bytes, but the outer member sender is only the
relay. A REST API key grants endpoint access; it does not create an actor
signature or business-governance vote.

### 8.2 Changes that do not require new genesis

| Change | Mechanism |
|---|---|
| Add, suspend, reactivate, or revoke an organization | Governed organization revision |
| Add an actor or change its organization, roles, status, or metadata commitment | Governed actor revision |
| Rotate, schedule, suspend, or revoke an actor key | Governed actor/key revision with proof of possession |
| Change the role required by a `governed-role` collection | Governed `DirectRolePolicyV1` revision |
| Change approval clauses, roles, counts, distinctness, rejection, or lifetime | Governed policy revision |
| Change administrator actors, threshold, or lifetime | Governed authority revision approved by the prior revision |
| Cancel a compromised pending proposal | Administrator threshold or authorized proposer cancellation |

Revisions are immutable. Current pointers advance monotonically and are
included under the state root.

### 8.3 Changes that require genesis or profile governance

| Change | Reason |
|---|---|
| Change a collection's authorization kind | Changes the collection trust contract |
| Bind a collection to another stable policy ID | Changes the authority namespace rather than policy contents |
| Add/remove/reorder components or workflows | Changes executable consensus code and state namespaces |
| Change schemas, codecs, limits, or authorization algorithms | Changes deterministic acceptance/root semantics |
| Change stable authority ID or governance algorithm | Changes the authority namespace/meaning |
| Enable governed routes on a previously basic-only profile | Expands the executable and attack surface |

For a new chain these choices are genesis-bound. For an existing chain they
require an explicitly cataloged, readiness-gated, height-activated ADR-015
profile transition with a reviewed state-migration contract. A node-local edit
is never sufficient.

### 8.4 Administrator authority is not silently coupled to membership

The default registry/policy administrator set is a set of stable actor IDs in
the current `AdministratorAuthorityV1`, not a set of genesis or current member
public keys. Administrator actor keys rotate through governed actor revisions
without changing the authority ID or actor ID. Any active member can relay a
valid administrator statement, so a planned or emergency member-key rotation
does not strand business authority and does not first require a profile change.

An administrator-authority revision is self-governed under the prior current
revision. This permits normal administrator succession and threshold changes
without silently coupling them to membership. It does not permit a single new
actor, member, REST caller, or compromised relay to add itself.

If enough administrator actors lose all usable keys to make the threshold
unavailable, recovery requires a cataloged ADR-015 profile transition or a new
chain generation. Before authenticated-map may rely on that path, composite
profile governance must support threshold cancellation/supersession while
`STAGING`, expose proposal age/expiry, and reject epoch exhaustion before a
proposal can become scheduled. Emergency membership rotation may happen first;
the recovery instruction must never require a compromised member key to remain
active.

The membership admin endpoints continue to govern `~governance/membership`;
they are not repurposed to carry arbitrary actor or policy mutations.

### 8.5 Revision and revocation timing

- A direct-role command must name the policy and actor revisions that are
  current at execution. A prior signature becomes unusable after relevant
  rotation, suspension, revocation, or policy activation.
- An approval proposal freezes its policy revision and digest when created.
- Each accepted decision snapshots the actor, organization, role, key, and
  revision facts checked at its decision height.
- Each accepted administrator decision likewise snapshots the authority,
  actor, organization, and key facts checked at its decision height.
- A governed mutation freezes the current administrator-authority revision and
  digest at proposal creation. Ordinary actor/policy mutation activation
  requires that authority revision to remain current.
- Activating a successor `AdministratorAuthorityV1` revision atomically marks
  every other still-pending mutation under the prior revision `SUPERSEDED` and
  removes it from pending/deadline capacity. A bounded per-authority pending
  index makes that transition's worst case a Phase-A consensus limit. Old
  administrator votes cannot remain as hidden future capabilities after an
  authority handover.
- A terminal approval is not retroactively erased by later rotation or role
  removal. It remains constrained by its original deadline and one-time
  execution claim.
- Compromise response for pending work is cancellation. Response to a
  previously executed terminal action is a new remediation/reversal action,
  not history deletion.

## 9. Query, proof, and projection surface

### 9.1 Root-fixed domain queries

The authenticated-map product exposes bounded typed queries for:

- collection metadata and resolved authorization capability;
- entry point lookup, including absence and revoked tombstones;
- command receipt and action commitment;
- authorization-consumption record;
- component command result/receipt;
- current and historical organization/actor revision;
- current and historical administrator-authority revision and accepted votes;
- current and historical direct-role/approval policy revision;
- approval proposal and accepted decision trail;
- bounded pending approval page; and
- bounded pending governance-mutation page.

Every exact-record domain response includes or is accompanied by:

- chain ID and `authenticated-map` state-machine identity;
- contract/domain-API version;
- committed height and state root;
- exact physical proof key and encoded record value; and
- current-pointer proof key/value when currency is asserted.

A bounded pending page is a deterministic projection of its committed pending
index rather than a state leaf. Its response carries the same chain/height/root,
the canonical page bytes, the source-index physical proof key, and an explicit
`DERIVED_FROM_PENDING_INDEX` verification label. It must not present the page
bytes as the value of that proof key. Verifying the full index or individual
pending markers is a separate proof operation.

JSON projections are conveniences. Canonical CBOR records and state proofs are
the verification boundary.

### 9.2 Bounded pending indexes

The role/governance components maintain deterministic, bounded indexes for
records currently in `PENDING` state plus bounded deadline buckets used by the
automatic expiry rule in §7.4. Ordering, page size, cursor format, maximum
pending count, maximum records per deadline, status transition, and replay
behavior are consensus contracts. A status transition, deadline-bucket removal,
pending-page update, statistics update, and command result are atomic.

The UI must not scan every historical proposal or reconstruct pending state
from potentially pruned message bodies. Statistics and list contents at one
height/root must agree.

### 9.3 Authenticated-map remains a point-query structure

The state machine does not add consensus range or full-map iteration merely to
support a browser. The console can:

- show the bounded genesis collection catalog;
- query an exact collection/key;
- show recently finalized commands/receipts from retained framework history;
  and
- use an optional rebuildable entry projection when configured.

An optional projection must be labelled `DERIVED` and report chain/genesis
identity, projector version, projected-through height/block, lag, and rebuild
status. A row becomes authoritative only after the client obtains and verifies
its exact point proof.

### 9.4 Composite proof bundles

Proof helpers support at least:

- basic authorization: entry/receipt plus finality and optional L1 anchor;
- direct role: entry, receipt/consumption, direct policy revision/current
  pointer, actor revision/current pointer, organization revision, and the
  accepted signature statement;
- approval: entry, receipt/consumption, terminal proposal, frozen policy,
  accepted decision trail, and retained actor/organization revision facts; and
- administrator governance: command result, mutation/proposal, authority
  revision/current pointer, accepted administrator statements, and retained
  actor/organization/key revision facts.

Bundles identify the root/height for every proof and reject mixed-root,
mixed-genesis, wrong-profile, missing-current-pointer, or payload-substitution
assemblies.

A proof against a later root can establish that an immutable
actor/policy/authority revision and consumption record are retained, but it
cannot by itself prove that a revision pointer was current at an earlier
decision height. Whenever a bundle claims historical currency, it includes the
pointer proof and finality certificate from the exact decision/execution root,
or explicitly relies on the state machine's proved consumption/decision record
without presenting that stronger historical-pointer claim. APIs and the
console must not blur those two levels.

## 10. Capability-gated authenticated-map console

### 10.1 Location and discovery

The operational UI is a built-in route in the unified Svelte console:

```text
/ui/app-chain/authenticated-map/?chain={chainId}
```

It is not part of App-Chain Studio. Studio authors and renders chain projects;
the unified console observes and operates a running chain.

The generic app-chain page shows an `Authenticated Map` link only when the
selected chain reports:

```text
stateMachine = authenticated-map
domainApi = authenticated-map-domain/v1
```

The route independently rechecks chain identity and API version before making
domain requests. A direct URL for another state machine displays a bounded
unsupported view and performs no authenticated-map parsing. In a multi-chain
node, switching the selected chain recomputes the capability.

Governed panels additionally require the genesis-authenticated capability
reported by the domain API. UI visibility is convenience, not access control;
the host API remains authoritative.

### 10.2 Required views

The first complete console provides:

1. **Overview** — chain/genesis/profile identity, finalized height/root,
   backend, collection count, validation catalog, and governed capability.
2. **Collections** — authorization kind/policy binding, restore rule, bounds,
   value encoding, schema/plugin descriptor, and initial-entry count.
3. **Entry lookup** — exact collection/key query, active/revoked/absent status,
   revision, controller where applicable, logical hash, bounded CBOR/hex view,
   receipt links, and proof retrieval.
4. **Mutations** — canonical PUT, PUT_IF_ABSENT, CAS, transfer, revoke, restore,
   and batch construction with local preflight and finality/receipt tracking.
5. **Actors and organizations** — current/historical revisions, roles,
   status, key epochs, governed activation facts, and exact proof keys.
6. **Policies and administrator authority** — current/historical direct-role,
   approval-policy, and administrator-authority revisions, clauses, actor IDs,
   thresholds, distinctness, status, and deadlines.
7. **Approvals** — pending/approved/rejected/cancelled/expired proposals,
   missing clauses, accepted decisions, blocks until deadline, action digest,
   and execution/consumption status.
8. **Governance changes** — pending registry/policy/authority mutations and
   their actor-signed approval/activation state, relay identity, expiry, and
   capacity result, clearly separated from business approvals.
9. **Proofs** — entry, absence, tombstone, receipt, actor, policy, proposal,
   consumption, finality, and optional anchor verification inputs.

Basic-only profiles show views 1-4 and 9. Views 5-8 appear only when governed
authorization is committed.

### 10.3 Safe write experience

The console may construct and submit canonical `open`, `owner`, and `member`
map commands through the host's authenticated API client, but it must
distinguish:

```text
HTTP accepted for sequencing
finalized in a block
state-machine applied or rejected
approval consumed and map entry changed
```

The console never asks for or retains actor/member seed phrases. For
`governed-role`, administrator-governance votes, and business approval
decisions, the initial workflow exports the canonical action/statement digest
for an external wallet, KMS, HSM, CLI, or application signer and imports the
resulting signed envelope. Browser signer integration requires a separate
reviewed key-custody decision.

Privileged member-governance actions require the normal unscoped privileged
API credential and explicit confirmation. Repeating a call through one member
does not fabricate additional votes.

### 10.4 Rendering and extension boundary

The console is host-owned reviewed code. It renders only typed server-owned
domain projections, bounded canonical CBOR, bounded hexadecimal data, and
reviewed stock view types.

Validator plugins may contribute data-only descriptors such as ID, contract
version, parameters digest, documentation identifier, or a reviewed stock
value-view hint. They may not contribute executable HTML, JavaScript, CSS,
templates, URLs, decoders, or format strings. Unknown/custom formats fall back
to bounded hex and downloadable canonical bytes.

The console uses no remote assets, `innerHTML`, untrusted API-prefix input, or
unbounded JSON/CBOR rendering. The corrected connection-origin contract below,
CSP, and host authentication remain in force.

### 10.5 API origin and credential binding prerequisite

The current generic console's independently persisted API base/key and
query-priority `?api=` behavior are not an acceptable security boundary for
this privileged route. Phase F is blocked until the shared client is corrected
for every console route, not only authenticated-map.

A persisted credential is stored and retrieved only as a record bound to the
exact normalized API base and origin selected through an explicit connection
action. A query parameter, deep link, saved base from another origin, redirect,
or capability response cannot cause that credential to be attached to a
different origin/base. Built-in host mode uses a verified same-origin relative
prefix. An explicitly configured external console connection may use another
origin, but its credential is session/persistence-bound to that exact origin
and the client refuses to set `X-API-Key` for any mismatch.

The production CSP restricts `connect-src` to the host and explicitly
configured console origins rather than broad `http:`/`https:` schemes. Browser
tests must prove that a link such as `?api=https://attacker.invalid` receives no
persisted credential and causes no credentialed cross-origin request. Redirect
rejection remains defense in depth rather than the origin-binding mechanism.

- console/domain-API capability metadata.

## 12. Security and trust boundaries

### 12.1 Authorization is not truth

A terminal proposal proves that registered keys holding configured roles
authorized an exact action under an authenticated policy. It does not prove
that an external document, product claim, inspection, identity, or measurement
is true. Applications and UIs must preserve that wording.

### 12.2 Replication is not confidentiality

Actor records, roles, policies, decisions, signatures, map values, and
consumption records are replicated to participating members and may be exposed
through retained proofs. Sensitive values need application encryption and
off-chain access policy. The console must not imply that API authentication
makes committed state confidential.

### 12.3 Policy weakening is a governance action

Changing a role or threshold can expand write authority. The mutation bytes,
old/new revision, proposer, approving administrators, activation height, and
result remain committed and queryable. A REST credential alone cannot produce
the required distinct actor signatures or lower a threshold.

### 12.4 Bounds and denial of service

V1 freezes maxima for:

- actors, roles, keys, clauses, and policy revisions per record;
- pending governance mutations and approval proposals;
- pending records per proposer actor and per policy/authority namespace;
- pending records assigned to one deadline height;
- decisions and distinctness checks per proposal;
- authorizations and covered indexes per map command;
- action, statement, signature, and receipt bytes;
- pending/list page sizes and cursors; and
- console response and rendering sizes.

Admission performs cheap canonical/bound checks before crypto.
`MapActorAuthorizationV1` and authenticated-map administrator statements carry
and sign their claimed public key, allowing stateless signature verification
without a component-state read. This filters malformed/random signatures but
is not treated as complete denial-of-service protection: a sender can create a
valid signature for an unregistered key. Authoritative apply requires the
claimed key to equal the current registered key and repeats the total
dual-verifier check. Reused ADR-019 approval-decision statements retain their
stateful key lookup and are covered by the same block work bound.

Phase A derives the maximum dual-Ed25519 verification count from all applicable
bounds: block bytes, block message count, maximum evidence items per command,
administrator votes, approval decisions, and key proofs. A reproducible JVM and
native benchmark on declared reference hardware must show that the complete
worst-case candidate fits inside the supported block interval with documented
headroom. If byte/message/evidence bounds alone do not satisfy that result, v1
adds a genesis-bound deterministic crypto-work-unit cap. The proposal builder
defers work beyond the cap, and followers reject a block exceeding it before
performing unbounded verification. Packing order is the existing deterministic
message order.

Crypto, schema, and plugin failures produce bounded deterministic outcomes
rather than leaking exception details.

### 12.5 Executable identity is fail closed

Component/provider versions, workflow descriptors, policy/actor crypto
contracts, validator artifact closure, state commitment profile, and domain API
version are release- and genesis-bound. A member missing or resolving a
different executable contribution fails before voting.

## 13. Compatibility and migration

### 13.1 Pre-release v1 reset

This amendment intentionally changes the intermediate development contract:

- collection descriptor and genesis bytes;
- state-machine assembly and physical state namespaces;
- command/evidence codecs and limits;
- genesis ID and format fingerprint;
- roots and proof keys for authenticated-map fixtures;
- receipts, clients, renderer output, and showcase configuration.

Those artifacts must be regenerated and reviewed. They are not required to
remain compatible with the unmerged branch baseline.

### 13.2 Boundaries that remain stable

- `kv-registry` state, commands, roots, and proofs are unchanged.
- The framework block/finality/anchor protocol remains unchanged.
- MPF and JMT backend algorithms and native proof formats remain unchanged;
  they commit a different final authenticated-map logical state.
- ADR-025.1 validators remain pure/state-free and keep their own frozen
  contract.
- The standalone `role-approvals` product keeps its existing public behavior;
  authenticated-map reuses its contracts/components through an explicit
  assembly.

### 13.3 Post-release rule

After a supported v1 artifact or genesis is published, a node must reject a
different contract/profile/genesis rather than reinterpret retained state.
Enabling governed authorization later requires a cataloged profile migration or
a new chain generation. It is not a configuration toggle.

## 14. Implementation plan

### Phase 0 — Dependency liveness and console-security prerequisites

## 15. Acceptance criteria

### 15.1 Contract and genesis

- All five authorization kinds round-trip through canonical genesis and reject
  unknown/non-canonical forms.
- Basic collection descriptors reject a policy ID; governed collection
  descriptors require one.
- A governed genesis is rejected unless its administrator authority, actor,
  organization, key/proof-of-possession, revision, and current-pointer closure
  is canonical, referentially complete, and threshold-satisfiable.
- Configured initial direct/approval policies become current revision 1
  atomically. An intentionally missing referenced policy is fail closed and
  reported by doctor/readiness with its stable ID.
- Changing authorization kind, policy ID, initial/stable authority binding,
  authority algorithm, component, workflow, limit, or executable artifact
  changes genesis/profile identity. A normal current-authority revision changes
  state and its root, not genesis identity.
- Independent Java and non-Java vectors agree on action commitments,
  statements, signatures, consumption keys, commands, receipts, and proofs.

### 15.2 Authorization correctness

- `open`, `owner`, and height-versioned `member` behavior matches the final
  reviewed v1 semantics.
- A current active actor with the required role/key can authorize exactly its
  signed action.
- Stale revision, wrong chain/genesis/action/policy/role/key, inactive actor or
  organization, mismatched claimed public key, invalid signature, deadline,
  and replay are rejected.
- Two eligible actors may independently use the same `authorizationId`; neither
  can consume or deny the other's `(actorId, authorizationId)`. The same actor
  cannot reuse that ID for another revision, key, policy, or action.
- Approval thresholds, AND clauses, distinct actors/organizations, rejection,
  cancellation, expiry, and frozen policy revisions behave deterministically.
- Payload, mutation order, value, precondition, collection, coverage, or policy
  substitution invalidates the authorization.
- A copied approval execution may be relayed first but cannot change the
  approved mutation/controller result; relay timing/receipt identity follows
  the explicit §6.4 contract.

### 15.3 Atomicity and replay

- A successful action writes every entry, receipt, pending-index transition,
  and consumption record atomically.
- A failed mixed batch changes none of them and consumes no evidence.
- The same direct authorization or approval proposal cannot execute twice,
  including after restart, catch-up, or snapshot restore.
- Approval consumption has exactly one key per proposal; no collection,
  coverage, or action-scope suffix permits a second successful execution.
- Multiple approved references in one batch are all consumed or none are.

### 15.4 Governance

- Actor, key, role, direct-policy, approval-policy, and administrator-authority
  changes require the configured distinct administrator-actor threshold and
  explicit activation.
- The new administrator-authority revision is approved under the prior current
  authority; it cannot authorize itself into existence.
- Activating that revision supersedes every other pending mutation under the
  prior authority, and no old-authority proposal can activate afterward.
- One member cannot create a business vote or multiply an imported actor vote
  through repeated endpoint calls or relays.
- Membership changes do not silently change business-policy administrators.
- Rotating/removing a member key before an emergency administrator action does
  not strand valid administrator actors; any remaining current member can relay
  their signed statements.
- A `STAGING` profile proposal can be threshold-cancelled/superseded, and
  profile-epoch exhaustion is rejected before scheduling rather than throwing
  first at activation.
- Same-block activation/action ordering is frozen and tested.
- Current-pointer and immutable-revision proofs agree at the same root.

### 15.5 Determinism and recovery

- Three independent members reproduce every root for basic, direct-role,
  approval, mixed-batch, governance, and value-validation workloads.
- MPF and classic JMT commit the same logical transitions under their expected
  native roots/proofs.
- Restart, rollback, replay, snapshot, late-member catch-up, pruning, and fault
  injection preserve actor/policy/map/consumption/index agreement.
- Expired proposal/mutation capacity is reclaimed automatically from bounded
  deadline buckets on empty and non-empty blocks. Saturation yields a stable
  result code, and capacity reopens without one poke command per stale ID.
- Per-proposer and per-policy/authority counts prevent one eligible actor or
  namespace from consuming more than its committed share of global capacity,
  and all count dimensions agree after every terminal transition.
- The derived worst-case dual-signature workload is published with JVM/native
  measurements and fits the supported block interval with the required
  headroom, or a deterministic crypto-work cap is enabled and tested.
- A generated governed chain is either genesis-ready or reports every missing
  policy/onboarding fact explicitly; interrupted optional onboarding is
  queryable and recoverable rather than silently half-writable.
- Wrong profile, genesis, executable bundle, validator artifact, or policy
  schema fails before voting.

### 15.6 Query and proof

- Entry, absence, tombstone, command result, actor, administrator authority,
  policy, proposal, pending/deadline index, and consumption queries are bounded
  and root-fixed.
- Direct-role and approval proof bundles reject missing pointers, wrong
  revisions, mixed roots, invalid finality, and wrong anchor bindings.
- Derived entry projections are never labelled authenticated enumeration and
  expose their exact lag/rebuild identity.

### 15.7 Console

- The generic page links to the authenticated-map console only for a selected
  `authenticated-map` chain with the expected domain API.
- The dedicated route independently rejects a wrong chain identity/API version.
- Governed panels appear only for a genesis-authenticated governed capability.
- Pending approval and governance pages agree with committed counts/status at
  one height/root.
- No actor/member seed is requested, transmitted, logged, or retained.
- Unknown/custom validator formats fall back safely without executing plugin UI
  code.
- `?api=` or any other deep link cannot cause a persisted key to cross its
  bound API base/origin; tests assert that no mismatched request carries
  `X-API-Key`.
- CSP, API-prefix, bounded rendering, authentication, responsive layout, JVM,
  and native distribution tests pass.

## 16. Alternatives considered

### A. Create `authenticated-approval-map` as a separate state machine

Rejected. It exposes implementation composition to users, duplicates map
configuration/documentation, fragments clients and UI, and still needs a clear
relationship with ordinary authenticated-map. One product can use an internal
composite without creating multiple app chains.

### B. Keep role approvals on another chain and bridge them off chain

Rejected as the authorization boundary. An external orchestrator cannot make
approval verification, exact payload binding, map application, and one-time
consumption atomic under one root.

### C. Add arbitrary actor-state reads directly to the existing class

Rejected. It bypasses declared component participants, hard-codes sibling keys,
and prevents safe reuse/evolution. The workflow is the cross-component
authorization boundary.

### D. Implement role checks as value-validator plugins

Rejected. Validators are state-free value predicates. Adding state, sender,
time, or role access would violate ADR-025.1 determinism and make validation an
authorization oracle.

### E. Keep the intermediate three-policy contract as v1 and add v2 now

Rejected. There is no published v1 compatibility boundary. Carrying two
contracts before first release creates permanent complexity without protecting
an existing user.

### F. Inline mutable role names and thresholds in collection genesis

Rejected. It makes normal personnel and policy changes chain-generation or
profile-migration events. Stable policy IDs with governed immutable revisions
separate trust binding from routine evolution.

### G. Automatically use current app-chain membership as policy administrators

Rejected as the default. A consensus-member rotation must not silently grant or
remove authority over business roles and thresholds. A future profile may
explicitly choose that coupling, but its semantics must be genesis-bound and
separately reviewed.

### H. Automatically execute the map when the last approval arrives

Rejected for the generic flow. The role proposal stores an exact payload hash,
not arbitrary map bytes, and the final approver's message should not implicitly
become an unrelated domain command. A final execution submission makes bytes,
preconditions, receipt, and consumption explicit while remaining atomic from
execution onward.

### I. Put a complete entry index in consensus for the console

Rejected. It duplicates map state, increases every root/update cost, and turns
a point-query product into a secondary-index product. Optional rebuildable
projections are the correct browsing layer.

### J. Allow validator/plugin-provided web components

Rejected. Executable UI contributions expand CSP and supply-chain risk and make
the trusted console depend on arbitrary application bundles. Reviewed
console-owned views plus data-only descriptors are sufficient for v1.

### K. Keep genesis-member administrators and rely only on profile governance

Rejected for authenticated-map governed profiles. The inner administrator set
would retain old member keys while the outer transport rejects them after
rotation, and the documented rescue path can itself be staging-blocked or
reach its epoch bound. Fixing ADR-015 liveness remains necessary, but routine
business administration uses stable actor identities and independently
governed key/authority revisions.

### L. Require every governed profile to bootstrap records after start

Rejected as the only v1 path. It leaves configured collections unwritable until
a multi-step ceremony completes and makes an interrupted ceremony an avoidable
deployment state. Canonical genesis records provide a closed ready-to-use
starting point. Optional post-genesis onboarding remains supported for records
intentionally omitted from genesis.

### M. Key direct consumption only by `authorizationId` or approval consumption by scope

Rejected. A global direct ID permits one actor to deny another actor using the
same caller-chosen bytes. A proposal-plus-scope key permits one approved action
to be consumed once per invented scope. Direct consumption is actor-namespaced;
approval consumption is exactly once per proposal.

### N. Bind approval execution to one member executor

Rejected as the default. Approval collections do not derive controller or
business ownership from the transport sender, so any member can safely relay
the exact approved action. The first eligible relay may determine timing and
receipt identity as stated in §6.4. A use case requiring executor identity or a
not-before rule needs an explicit signed policy field/version rather than an
implicit transport convention.

## 17. Consequences

### 17.1 Positive

- One authenticated-map product covers member-, actor-, and approval-governed
  registries without application-specific consensus code.
- Business identity stays separate from consensus membership while sharing one
  final state root.
- Exact payload binding and atomic consumption remove the off-chain bridge gap.
- Stable policy IDs permit governed operational evolution without node-local
  forks or routine chain migration.
- Stable administrator actors survive member-key rotation and can govern their
  own authority revisions without silently making new members business admins.
- Canonical genesis records let generated governed chains start from a complete,
  diagnosable authorization configuration.
- Deadline buckets turn pending bounds into a deterministic liveness contract
  rather than an operator-driven cleanup procedure.
- Common proofs, clients, docs, showcase, and console can serve many products.
- The capability-gated UI makes pending authorization and governance visible
  without weakening generic-console or plugin boundaries.

### 17.2 Costs

- The final v1 command, genesis, state, proof, and test surface is materially
  larger than the intermediate simple map.
- Even basic profiles carry a reviewed product assembly and capability metadata;
  governed profiles additionally retain actors, revisions, decisions,
  signatures, initial governance records, deadline indexes, command results,
  and consumption records.
- Actor-authenticated administration adds signing/client/proof surface beyond
  the existing member-key governed-mutation adapter.
- Crypto and cross-component reads increase candidate-validation cost and need
  explicit measured limits.
- The current branch's authenticated-map genesis, roots, vectors, clients,
  showcase fixtures, and qualification records must be regenerated.
- A useful console requires typed domain APIs and bounded indexes that would not
  otherwise be needed for point lookup alone.

### 17.3 Operational implications

- Operators choose and verify the genesis administrator actors, organizations,
  public keys/proofs, threshold, and initial policies before rendering genesis.
  They preserve administrator-actor threshold availability independently of
  membership rotation.
- Intentionally omitted policies keep only their referenced collections fail
  closed and are reported by readiness/doctor until governed onboarding
  completes.
- Losing enough administrator actor keys for the threshold requires the
  explicit profile/new-genesis break-glass path; rotating a member key neither
  causes nor repairs that loss.
- Applications must distinguish member relay identity, domain actor identity,
  business approval, finality, and L1 anchoring.
- Actor private keys stay in wallets/KMS/HSM/application custody; Yano stores
  public authorization facts and signatures only.
- Policy and actor histories grow monotonically and need published sizing,
  retention, snapshot, and proof-support bounds.
- Operators monitor pending/deadline-bucket occupancy, expiry results, and
  crypto-work utilization before they become capacity pressure.

## 18. Contract-phase measurements and frozen choices

Phase A froze the following v1 maxima: 32 evidence items, 128 covered mutation
indexes, 64 genesis organizations, 128 actors, 256 actor keys, 128 policies,
64 administrator actors, and 262,144 governed-genesis bytes. Pending capacity
is 1,024 governed mutations and 4,096 approval proposals, with 64 per actor,
256 per policy, 256 per authority, and 128 per deadline. A block may expire 256
records, supersede 256 records during authority handover, and return 100 items
per bounded page.

The strict dual-verifier benchmark rejected an initial 2,048-unit crypto cap.
The final cap is 512 governed actor signatures per block, approximately 201.6
ms or 10.1% of the default two-second interval on the Phase-A Java 25 reference
run. Phase G must repeat the measurement for the supported native runtime.

Registry/authority mutations use typed `actors.command.v1` commands. Direct
and approval policy mutations use typed `role-approvals.command.v1` commands
owned by the same declared role workflow. Exact CBOR, hashes, preimages, error
codes, retention records, index semantics, state keys, and the remaining bounds
are published in the CDDL and the
[Phase-A record](025.2-phase-a-contract-and-work-bounds.md).

Any answer that introduces ambient state, weakens exact action binding, permits
uncommitted policy/UI behavior, changes one-time consumption, or splits
authorization and map application across roots requires this ADR to be amended
before implementation.

## 20. External-review disposition

The pre-implementation review against the live tree produced the following
contract corrections:

- **Administrator rotation and rescue:** confirmed. Genesis-member keys are not
  the authenticated-map business authority. Stable administrator actors,
  governed authority revisions, and Phase-0 composite-profile liveness fixes
  replace the previous operational instruction to update a profile before
  rotating membership.
- **Pending saturation:** confirmed for approvals and governed mutations.
  Deadline buckets, per-deadline bounds, automatic expiry, and authenticated
  capacity results replace silent no-op plus per-ID poke recovery.
- **Approval-consumption ambiguity:** confirmed. One proposal has exactly one
  authenticated-map consumption key; "action scope" is removed.
- **Cross-actor direct-ID griefing:** confirmed. Direct consumption is keyed by
  `(actorId, authorizationId)` and has an adversarial collision criterion.
- **Genesis bootstrap:** adopted as a v1 capability and required for the minimum
  administrator closure. Genesis records improve readiness, but they solve the
  rotation defect only together with actor-authenticated administration.
- **Consensus crypto cost:** confirmed as a qualification risk. Self-contained
  direct/admin signatures improve admission, while a derived worst-case block
  bound and optional deterministic work cap provide the actual resource fence.
- **Console API origin:** confirmed as an existing shared-client prerequisite,
  not merely an authenticated-map UI concern. Phase F cannot begin until the
  persisted credential is exact-origin/base bound.
- **Admission versus apply:** same-block stateful authorization ordering is now
  explicit. ADR-025.1 is not contradicted: its equivalence claim remains only
  for the pure value-validator verdict.
- **Relay front-running:** the original owner-capture problem is structurally
  absent for approval collections, but inclusion height and receipt identity
  remain relay-selected within the approved window and are now stated rather
  than described as identical state.
