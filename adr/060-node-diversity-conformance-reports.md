# ADR-060: Node-Diversity Conformance Reports

**Status:** Accepted. Implementation in progress (phases below).
**Date:** 2026-10-23
**Authors:** Claude Code (Opus 5.5)
**Related:** ADR-056 (Conway Java ledger rules, `ledger-conformance` harness), ADR-057 (Amaru wasm validator),
`ledger-conformance/`, `.github/workflows/release-dist.yml`

## Context

[Cardano Node Diversity](https://pragma-org.github.io/node-diversity-conformance/)
([repository](https://github.com/pragma-org/node-diversity-conformance)) compares independent node implementations
on shared test corpora. The site runs nothing itself. Each node publishes one JSON report per scenario from its own
CI, and the site downloads the latest reports when it builds. Each scenario is a quarter of a node's overall score.
cardano-node, Amaru and Dingo are listed today.

| Scenario | Kind | Corpus | Report entry |
|---|---|---|---|
| `ledger-rules` | functional | 284 transaction fixtures in the pragma repository, `scenarios/ledger-rules/fixtures/` (Amaru's fixture format) | `{id, result}`: `"pass"`, a predicate name from the scenario schema, or `"DecodingFailure"` |
| `uplc-conformance` | functional | 1,064 UPLC vectors (`uplc-conformance.tar.zst`), protocol versions 10 and 11, cost models included | `{id, title, group, plutus_version, protocol_version, evaluation, budget}` |
| `uplc-turbo` | performance | 3,997 Flat-encoded mainnet scripts (`turbo.tar.zst`), by epoch | per script: `cpu_us`, `mem_bytes`, `budget_cpu`, `budget_mem`, plus the machine |
| `cbor-decoding` | functional | `r2rationality/cardano-cbor-dataset`, `dataset/conway`: 25 CDDL rules, 866 valid and 8,334 invalid samples | per-rule and total `*_expected` / `*_actual` counts |

### How the other nodes do it

Amaru and Dingo both generate the four reports **in their main node repository**, in the release workflow, and attach
them to every GitHub release:

- **Amaru:** a reusable `template-conformance-reports.yml` with one job per scenario, called from `release-begin.yml`.
  The harnesses are tests and benches in the node's own crates (`make conformance-*`). Assets are named
  `amaru-<version>-<scenario>.json`.
- **Dingo:** `publish.yml` on version tags. It checks out the CBOR dataset and pragma's fixtures at pinned commits and
  pins the two UPLC tarballs by SHA-256. It runs one Go command per scenario (`internal/*conformance/cmd`) and uploads
  `dingo-<version>-<yyyymmdd>-<scenario>.json.gz`. A generator that fails writes an error report rather than failing
  the release.

The pragma site picks each node's newest dated asset through
`{"github_releases": "<org/repo>", "asset": "<node>-*-<scenario>.json"}` in `nodes/<node>/metadata.json`.

### What Yano already has

- **ledger-rules:** `ledger-conformance` (ADR-056 §8) already loads Amaru's fixture format (`AmaruScenarioLoader`) into
  an `InMemoryLedgerView` and runs every engine on it. Run on pragma's 284 fixtures (2026-10-23, `main` a4e28babf),
  `java-julc` gets the verdict right on 284/284. Its first failure matches the fixture on 281, and the expected
  predicate is among its failures on 283. For comparison, cardano-node and Amaru each score 277/284; their reports
  predate the seven newest fixtures.
- **uplc-conformance:** julc's Java CEK machine (`org.julclang:julc-vm-java`) is Yano's phase-2 evaluator for
  `java-julc`. julc's own test suite runs the official Plutus conformance vectors, and julc can parse and print
  textual UPLC (`UplcParser`, `UplcPrinter`).
- **uplc-turbo** and **cbor-decoding:** nothing.

## Decision

### 1. One module: extend `ledger-conformance`

The four report generators live in the existing test-only `ledger-conformance` module. They go in package
`org.yanoproject.ledger.conformance.diversity`, with one subpackage per scenario (`ledgerrules`, `uplc`, `turbo`,
`cbor`) and a shared report writer. There is no new top-level folder and no submodule per scenario:

- **Reuse.** The ledger-rules report has to run the same engine adapter, case loader and failure naming that the
  module already holds (`JavaViewEngine`, `ScenarioCases`, `AmaruCorpusNames`). A separate module would duplicate
  them.
- **Dependencies are already in place.** The UPLC scenarios need `script-evaluators` (julc), and the CBOR scenario
  needs `ledger-rules` (Yano's strict transaction decoder) and CCL. The module already depends on all three.
- **KISS.** Four submodules would mean four build files with the same dependencies and nothing to separate. The
  module stays unpublished (ADR-056 §8).

### 2. Reports are generated by tests, as the module's other reports are

Gradle task `:ledger-conformance:nodeDiversityReports` follows the existing `conformanceReport` task:

- It runs the `*DiversityReportTest` classes with `-PnodeDiversityCorpora=<dir>`, or the environment variable
  `NODE_DIVERSITY_CORPORA`.
- That directory holds the extracted corpora: `node-diversity-conformance/`, `cardano-cbor-dataset/`,
  `uplc-conformance/` and `turbo/`.
- Each test writes `build/node-diversity/yano-<version>-<yyyymmdd>-<scenario>.json`.
- A scenario whose corpus is absent is skipped and writes nothing.
- A score below 100% never fails the task. A test fails only when the harness itself breaks, or a report would not
  match the scenario's schema.
- The ordinary `test` task runs each generator's unit tests on small in-repository samples. It never needs the
  corpora.

The corpus revisions are pinned in `ledger-conformance/node-diversity/corpora.env`: git commits for the two
repositories and SHA-256s for the two tarballs. `ledger-conformance/node-diversity/fetch-corpora.sh <dir>` fetches and
verifies them. Each report records the corpus it ran on where the schema allows (`corpus` for CBOR).

### 3. ledger-rules: the default engine, reported the way the Haskell reference reports

- **Engine:** `java-julc`, Yano's default admission and shadow-sync engine, under rule `LEDGER`, origin `SYNC`, via
  the module's `JavaViewEngine`.
- **Result selection** matches cardano-node's report. That report is produced by Amaru's Haskell checker
  (`crates/amaru/tests/conformance/validation-rules`, `Command/ValidatePhaseOne/Run.hs`):
  - accepted gives `"pass"`;
  - a decoding failure gives `"DecodingFailure"`;
  - when the fixture's expected predicate is among the engine's failures (Haskell name, through `AmaruCorpusNames`
    and its aliases), the result is that predicate;
  - otherwise the result is the first failure mapped to its corpus name, or its bare Haskell constructor when no
    corpus name exists.

  This rule matters because Haskell's STS ordering puts `UTXOW` failures before `CERTS` failures (`RuleFrame`). A
  fixture can name a predicate that Haskell reports second, and both Haskell's checker and pragma's own cardano-node
  report treat "among the failures" as a match.
- **Loader changes:** the corpus-name table gains the two names the newest fixtures use (`DRepNotRegistered`,
  `StakeKeyNotRegistered`). The loader also accepts pragma's layout, where shared documents sit beside `scenarios/`
  rather than under `common/`.
- **Expected score:** 283/284. Fixture 00280 expects `OutputTooBigUTxO` for a Byron address with oversized
  attributes. In Haskell that transaction fails only `OutputBootAddrAttrsTooBig`: `validateOutputTooBigUTxO` measures
  the serialized *value* (`Alonzo/Rules/Utxo.hs`), and Babbage/Conway run both checks. Yano agrees with Haskell. The
  fixture is reported upstream rather than worked around.

### 4. uplc-conformance: julc, as phase 2 runs it

The harness follows Amaru's `crates/amaru-uplc/tests/conformance.rs`, which defines the ids:

- **Ids and labels:** `<path below the Plutus-version folder, non-alphanumerics as _, lower case>_<v1|v2|v3>`, with
  the group (the grandparent path) and title (the folder name, `-`/`_` as spaces) taken from the path.
- **Evaluation:**
  - decode the vector's `.flat` program when it has one, as phase 2 decodes a script (`JulcScriptAdapter.toProgram`:
    `UplcFlatDecoder` with the decoding limits of the protocol version and language). On chain, scripts are Flat, so
    this is the decoder Yano depends on. A vector with no Flat form (a `value` constant) is parsed from its text;
  - reject what the protocol version or Plutus version does not allow (program version 1.1.0 before protocol 11, and
    builtins unavailable for the language and protocol), as Haskell's decoder does (`ProgramValidator`);
  - evaluate on `JavaVmProvider` with the corpus cost model for (protocol, language) and a budget of 10B CPU / 14M
    memory.
- **Reporting:**
  - when the result term is alpha-equivalent to the parsed expected output, the report carries the expected text
    (Amaru does the same), and otherwise julc's printing of the result;
  - errors are `"parse/decode error"`, `"out of budget"` or `"evaluation failure"`, with a `null` budget;
  - budgets are the consumed CPU and memory.

### 5. uplc-turbo: julc, measured on the JVM

- **Input:** each sample is a CBOR byte string holding Flat bytes, decoded before timing. The protocol version is
  taken from the epoch folder (≥644: 11, ≥537: 10, ≥507: 9, else 8), and the language from the file-name suffix.
- **Cost models:** the default cost models of that protocol version and language, as the scenario requires.
- **Measurement:**
  - JIT warm-up runs first, and do not count;
  - then 50 evaluations, keeping the best 30 by time;
  - `cpu_us` is the mean of `System.nanoTime` around evaluation only;
  - `mem_bytes` is the mean of the evaluating thread's allocated bytes
    (`com.sun.management.ThreadMXBean.getThreadAllocatedBytes`). This is the JVM's counterpart of Amaru's arena bytes
    used.
- **Budgets:** CPU and memory are counted with the 10B / 10M budget the scenario sets.
- **Machine block:** OS, architecture, CPU, logical cores and memory, from `java.lang.management`.

### 6. cbor-decoding: Yano's transaction-validation decoder

The scenario is meant to exercise the decoder the node relies on. In Yano that is the transaction-validation path:

- CCL's model decoders (`Transaction.deserialize` and the element types it uses), which `java-julc` decodes with
  first;
- followed by Yano's strict `RawTransaction` family (`StrictCbor`, `RawOutput`, `RawCertificate`, `RawProposal`,
  `RawParamUpdate`, `RawVoter`, `RawAuxData`, `PlutusData`), which apply Haskell's decoding rules.

For each corpus rule:

- **valid** samples must pass both decoders and re-encode to the reference:
  - for the seven hashed rules (`auxiliary_data`, `header`, `native_script`, `plutus_data`, `redeemers`,
    `transaction_body`, `transaction_witness_set`), byte for byte, from the preserved original bytes, as Haskell's
    `MemoBytes` does;
  - for every other rule, after re-encoding the decoded CCL model and normalizing it with the dataset's normalization
    specification. The normalizer must reproduce the dataset's 20 normalization vectors.
- **invalid-zap-0..3** samples must be rejected by the decoder pair.

Rules no transaction path decodes on its own are decoded through their production entry point: `block` and `header`
through CCL's `RawBlock`, as shadow sync decodes blocks. The report carries per-rule counts in the format of Amaru's
report, `corpus: "conway-123-100"` and `protocol_version: "10.0"`.

The decoder sync uses (yaci's `BlockSerializer`) is lenient and is not what this scenario measures. Any divergence
the corpus exposes in the validation decoders is fixed at its source in its own change. It is never masked in the
harness.

### 7. CI: a reusable workflow, called by the release

- `.github/workflows/node-diversity-reports.yml` (`workflow_call` and `workflow_dispatch`):
  - fetches the pinned corpora with `fetch-corpora.sh`;
  - runs `nodeDiversityReports`;
  - uploads the JSON files as artifact `node-diversity-reports`.
- `release-dist.yml` calls it on release tags, and its `release` job attaches `dist/yano-*-*.json` beside the zips.
- A manual dispatch on any branch produces the reports without releasing, to check scores before a release.

### 8. Publication (outside this ADR's implementation)

A PR to `pragma-org/node-diversity-conformance` adds `nodes/yano/` with `metadata.json`, `README.md` and a logo. The
metadata uses `{"github_releases": "bloxbean/yano", "asset": "yano-*-<scenario>.json"}` for each scenario, and the
maintainers open it once a release carries the reports.

## Consequences

- Yano can be listed beside cardano-node, Amaru and Dingo with reports from its own release pipeline.
- The corpora become regression inputs for the ledger rules, julc and the transaction decoder. A new corpus revision
  is a deliberate pin change, and its score changes show up in the diff of the generated reports.
- julc is evaluated as Yano runs it. Divergences in julc are fixed in julc, which needs a julc release and a Yano
  bump (the julc issue workflow).
- The CBOR scenario may surface decoding divergences in CCL or Yano's strict decoder. Those are real consensus risks
  and are tracked as their own fixes.
