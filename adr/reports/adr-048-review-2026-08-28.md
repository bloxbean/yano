# ADR-048 review — bounded memory during epoch boundary processing

Date: 2026-08-28
Reviewed: `adr/048-bounded-memory-epoch-boundary-processing.md` (Proposed)
Method: every factual claim in the ADR was checked against the current source on
`fix/byron-address-projection-resolver` (worktree `node-wallet-apis`). Line numbers
below refer to that tree.

## Verdict

The diagnosis is sound and code-verified: the boundary really does build several
network-sized object graphs at once and then holds them across a large native
batch. The proposed direction (consume the already-maintained `utxo_stake_balance`
index, stream SNAP/DRep, shorten reward lifetimes, bound writes) is the right one,
and the acceptance gates are the right shape for a "no regression" rollout.

It is **not implementable as written**. Five amendments are required before Phase 1
starts; two of them (F1, F3) would produce wrong or failing boundaries on existing
chainstates if the ADR were followed literally. A sixth point is a sequencing
recommendation: the highest-risk part of the ADR (Section 6, chunked journals and
v2 rollback) should be gated on Phase 0 evidence rather than committed up front.

## Required amendments

### F1 — Section 3 substitutes an index that is not guaranteed complete

Section 3 replaces the snapshot's network-wide `PREFIX_STAKE_EVENT` scan
(`DefaultAccountStateStore.java:3937-3963`) with `PREFIX_ACCT_DEREG_COORD`. That
index is written for every deregistration in every era
(`DefaultAccountStateStore.java:3362-3368`, inside `deregisterStake`, no era gate),
but it cannot be assumed complete on the stores the ADR targets:

- It was introduced as a *pointer-resolution* index. Its completeness marker
  `META_POINTER_INDEX_GENESIS` is refused on any chainstate that has already
  advanced (`markPointerIndexFromGenesis`, `:3110-3125`: "projection history is
  fresh-sync only"). Upgraded mainnet stores predate the index and have no rebuild
  path — unlike `utxo_stake_balance`, which has `StakeBalanceIndexStartupMigration`.
- `cleanupPointerIndex(throughSlot, maxKeys)` (`:3145-3165`) is a public
  maintenance contract that deletes index entries. It has no caller today, but the
  contract exists and the snapshot merge would silently lose "deregistered after
  delegation" facts the moment anyone wires it.
- The authoritative event log is retained forever (`pruneOldStakeEvents` at
  `:4210` has no callers; comment at `:2650` says events are not pruned), so a
  rebuild source exists.

Required: either (a) add a bounded rebuild of `PREFIX_ACCT_DEREG_COORD` from
`PREFIX_STAKE_EVENT` with its own versioned ready marker, and make Section 3's
merge require that marker exactly as it requires the stake-balance marker; or
(b) keep the event scan for this one input. Also state that `cleanupPointerIndex`
must be refused (or must invalidate the marker) while the snapshot path depends
on the index. Without this the streaming SNAP produces a different snapshot than
the legacy path on upgraded stores, and the differential tests on fresh fixtures
will not catch it.

### F2 — an existing crash-resume defect the ADR fixes without knowing it

`EpochBoundaryProcessor.java:351-369`: when a boundary resumes past
`STEP_SNAPSHOT`, `utxoBalances` stays `null` and is passed to governance (`:417`).
`DRepDistributionCalculator.java:170-176` then falls back to
`getSnapshotStake(...)` (`:300-318`), which returns the pool snapshot `amount()` —
already UTXO **plus** reward balance — and then adds `rewards` again. Result on a
crash-resume between SNAP and governance: reward balances double-counted in the
DRep distribution, and DRep delegators that are not pool-delegated get zero UTXO
stake. The same fallback triggers if the stake snapshot service is disabled.

Consequences for the ADR:

1. Section 4 (governance opens its own coordinate-bound view) structurally removes
   this defect. Say so, and add "DRep distribution after a crash-resume equals the
   no-crash result" to the Phase 2 exit gate — today it does not.
2. The parity gates say "logically identical to the accepted legacy result". The
   legacy result is not crash-deterministic. Every differential fixture must be
   generated from a **no-crash** legacy run, and the crash-injection suite must
   compare new-path-with-crash against new-path-without-crash, not against legacy.

### F3 — the coordinate the view must prove is not stored today

Section 2 requires the view to capture "an exact canonical block number, slot and
hash" from the same RocksDB snapshot and to fail closed on mismatch. The UTXO
store persists `META_LAST_APPLIED_SLOT` and `META_LAST_APPLIED_BLOCK`
(`DefaultUtxoStore.java:2092-2093`) but no block hash. As written, `index` mode
would fail every boundary on every existing store, and `auto` mode would take the
fatal path after view creation.

Required: Phase 1 must first add the block hash to the UTXO apply batch (same
batch as the UTXO mutations and the stake-balance deltas), define what the check
does for stores that predate the hash (treat as unverifiable → scan fallback
*before* view creation, which Section 8 already allows), and only then enable the
strict check. The fail-closed assertion is still worth having: event delivery is
synchronous only because subscriptions default to no executor
(`PropagatingEventBus.java:222`), and `BodyFetchManager.java:1698-1726` publishes
all three transition events inline — nothing structural prevents a later refactor
from weakening that.

### F4 — Section 5c overstates the reward-library problem and contradicts ADR-049

`cf-rewards-calculation` 1.0.2 exposes
`PoolRewardsCalculation.calculatePoolRewardInEpoch(...)` as a public static
method. The fetched source of `EpochCalculation.calculateEpochRewardPots` is pure
scalar accumulation around that per-pool call: reward pot and treasury cut,
unclaimed retired-pool deposits, MIR adjustments, per-pool distributed and
unspendable totals, `undistributed → reserves`, `unspendable → treasury`, and the
Allegra bootstrap adjustment. None of it needs the full result list; the list is
only assembled for the return value.

A Yano-owned pool-at-a-time orchestrator therefore needs **no fork, extension or
upstream change** — which is exactly what ADR-049 already states. ADR-048 should
adopt that reading, drop "extend, fork or upstream" from Section 5c and the
"requires an API change, fork or upstream contribution" consequence, and instead
pin the library version and add a golden-parity test that the orchestrator's
scalar totals equal `calculateEpochRewardPots` on every retained fixture. The
open question 5 ("can upstream accept the API") becomes moot.

Two library details the orchestrator must reproduce exactly: per-pool
`stakeAddresses` is the reward address plus delegators, and the deregistered /
late-deregistered sets are intersected against that per-pool set; and pools are
iterated in `poolsThatProducedBlocksInEpoch` order with a `findFirst` lookup into
`poolHistories` (order does not affect totals, but the parity test should prove
it).

### F5 — artifact-reference atomicity changes under chunked generations

Today the ADR-039 epoch-stake artifact reference and `META_LAST_SNAPSHOT_EPOCH`
ride in the same `WriteBatch` as all snapshot rows
(`DefaultAccountStateStore.java:4091-4104`, "neither can become durable without
the other"). Once rows are chunked, that guarantee must move to the `COMPLETE`
marker commit: the reference, the last-snapshot metadata and the archive writer
commit all belong to the final chunk, and a `BUILDING` generation must read as
*pending* to the ADR-045 gap logic, never as a gap or as a zero-row completion.
The ADR gestures at this in constraint 10 but should name the mechanism. The same
applies to the reward archive writer, which today commits right after
`db.write` (`EpochRewardCalculator.java:165-185`).

## Sequencing recommendation (the "no regression" lens)

The ADR commits to Section 6 — v2 chunk journal, versioned phase descriptor
table, resumable rollback state machine, v1/v2 mixed decoding — before Phase 0 has
measured whether the reward `WriteBatch` is a top-three contributor. Section 6 is
the only part of the plan that rewrites recovery and rollback semantics, and
therefore the only part with a realistic chance of introducing a *ledger*
regression rather than a memory one.

Source-level reading suggests the peak is dominated by Java object graphs, not by
the batch. Rough estimates from the code (to be replaced by Phase 0 numbers):

| Structure | Where | Rough size on mainnet |
|---|---|---|
| UTXO credential map: `CredentialKey(int, String hex)` → `BigInteger` | `UtxoBalanceAggregator.java:51,90` | ~1.5–2M entries × ~150–200 B ≈ 300–400 MB |
| Snapshot map: `"credType:credHash"` String → record(poolHash String, BigInteger) | `EpochRewardCalculator.java:1080-1099` | ~1.3M × ~250 B ≈ 300 MB, **including ~1.3M duplicate 56-char `poolHash` strings** for ~3k distinct pools |
| `Delegator` objects + per-pool `List` + `new HashSet<>(list)` copy | `:552-563, :622` | another ~150–250 MB, all alive at once |
| Account sets: `getAllRegisteredCredentials()` + two/three `HashSet<String>` from slot-0 event scans | `:914-916, :949-969`; `DefaultAccountStateStore.java:1359, :4238-4270` | several sets of ~1M+ strings each |
| Reward `WriteBatch` + `List<DeltaOp>` + overlay + encoded delta | `EpochRewardCalculator.java:138-142`; `DefaultAccountStateStore.java:4905-4927` | proportional to positive rewards (~1M), likely 100–200 MB |

If that ordering holds, Phases 1–3 (index-driven SNAP/DRep, lifetime reductions)
remove the overlap that produces the multi-gigabyte peak, and Section 6 becomes a
second-order optimization. Recommendation: keep Section 6 in the ADR as a
*conditional* phase with an explicit Phase 0 trigger (e.g. "reward-commit phase
peak > X MiB after Phase 3"), the same way Section 7 already conditions Phase 0B
on measurement. That keeps the memory target while removing the largest
regression surface from the critical path.

## Zero-ledger-risk quick wins the ADR does not list

These change no arithmetic, no persistence and no ordering; they belong in Phase 3.

1. **Intern `poolHash` in `getStakeSnapshot`** (`EpochRewardCalculator.java:1094`).
   ~1.3M duplicate strings collapse to ~3k. Likely >100 MB on mainnet for one line.
2. **Stop materializing `stakeSnapshot` as a map before `buildPoolStates`.** The
   map is used for `totalActiveStake` (a scalar), grouping by pool, and a
   `keySet()` fallback loop in `buildAccountSets` (`:990-996`). Group directly
   while iterating the snapshot CF; the fallback loop can iterate the CF a second
   time. Removes one of the two full copies without needing the pool-major
   projection of Phase 4.
3. **`forEachUtxoAtSlot` should set `ReadOptions.fillCache(false)` today**
   (`DefaultUtxoStore.java:515-538`). The pattern already exists in
   `DirectRocksDBChainState.java:461`. This is the ADR's own Section 2
   requirement, but it applies equally to the legacy scan and costs nothing.
4. **Intern / compact `CredentialKey`.** The hex `String` in
   `UtxoBalanceAggregator.CredentialKey` is ~3× the size of the 28-byte hash.
   A record over `byte[]` (or a `long`-pair key) roughly halves the UTXO map. The
   cf-rewards `Delegator.stakeAddress` must stay a String, so this applies to the
   UTXO map and the snapshot merge, not to the reward input.
5. **Timeout fallback doubles the scan.** `utxoBalancesFuture.get(300, SECONDS)`
   falling back to an inline scan (`EpochBoundaryProcessor.java:357-362`) means a
   slow disk pays the 30–60 s scan twice with both results briefly alive. Either
   wait without timeout or fail; the ADR's strict/auto modes should specify which.

## Smaller notes

- Section 1 phase list omits `mir-credit` (`creditMirRewardRest`, run before the
  parallel scan starts, `EpochBoundaryProcessor.java:326-328`) and the PV10
  reverse-index rebuild (`:398-407`), which can itself touch every DRep
  delegation. Both should be instrumented.
- Section 3, check 4 ("a later deregistration did not invalidate the delegation")
  and check 5 (reg-slot) are already null-tolerant for `PREFIX_ACCT_REG_SLOT` in
  the current code (`:4025-4033`). The merge must keep the same tolerance rather
  than treating a missing reg-slot row as a failure.
- Section 6 "Accumulated reward semantics": today `creditReward` reads through the
  overlay first (`EpochRewardCalculator.java:748`), so chunk flushes that clear the
  overlay must guarantee the flushed value is visible to `db.get` before the next
  credit — i.e. flush must be a committed `db.write`, not a queued one. The ADR
  says this; the test in "Chunk journal" should assert it with two rewards for one
  credential straddling a chunk boundary.
- The `cleanupPointerIndex` javadoc says the dereg-coord index "only ever holds
  pre-Conway deregistrations" (`:3160`), but `deregisterStake` writes it
  unconditionally in every era (`:3362-3368`). Stale doc; worth fixing regardless
  of which F1 option is chosen, because it is why the index's completeness story
  is easy to misread.
- The rollback code comment "AdaPot entries bypass delta tracking" (`:4576`) is
  partly stale — `storeAdaPotBatch` is delta-aware in the reward path. The v2
  phase descriptor table is a good place to make AdaPot's rollback story explicit.
- `Expected processing-time impact` is plausible: the current SNAP does two point
  `db.get` per pool delegation plus a full event-log scan; an ordered merge should
  be faster, not merely smaller. The one place time can regress is the pre-Conway
  fallback if the parallel scan is serialized — the ADR already says so.

## Answer to "without creating any regression"

The ADR's gates (logical-digest parity, crash and rollback fault injection, ±5 %
boundary time, <2 % sync throughput, mainnet RSS on each reference class) are the
right instruments. The concrete regression vectors this review found are:

1. **F1** — wrong snapshots on upgraded stores if `PREFIX_ACCT_DEREG_COORD` is
   trusted without a completeness marker. Fresh-sync fixtures will not detect it.
2. **F3** — strict/auto index mode failing or falling to the fatal path on every
   existing store because the block hash is not persisted yet.
3. **F2** — parity fixtures generated from a legacy path that is itself
   non-deterministic under crash-resume, which can mask or misattribute diffs.
4. **Section 6** — recovery/rollback semantics rewrite on the critical path before
   measurement shows it is needed.

With F1–F5 amended and Section 6 made conditional on Phase 0 evidence, the ADR is
ready to accept for implementation.
